## Hard stops before a migration proposal

- [ ] Verify the intended base, target service, database identity/realm, storage and backup boundaries independently. No production contact or credential change is needed for this local review. Require a target-specific implementation/release plan before any installation.
- [ ] Establish one independently enrolled **current target-local** owner subject, with protected provenance/current incarnation, active control/ready identity evidence and native app-issued authentication. The real Stage owner loader is absent and the reference explicitly denies numbering admission. Do not promote a legacy admin, trust a username/ID/settings value, or add a parallel owner table to bypass that prerequisite. Test current owner, other admin, disabled/revoked owner, stale activation epoch, wrong realm, copied account/credential, and service/store failure; reject unknown authority without fallback.
- [ ] Confirm actual schema and migration lineage against the registry/checksums and intended source. Stage contains 0087/0089 but no 0080; do not infer 0090 ancestry, replay a count-only readiness check as proof, edit/reuse a previously applied migration, or adopt a ledger by hand. Draft an additive, idempotent deployment-specific migration only after legacy data/role compatibility is established. `scripts/review/*.pg18.sql` are synthetic-only, refuse other database names, and are not production migration inputs.
- [ ] Verify the physical role graph, object ownership/DDL and direct sequence privileges, common locks, startup, pooled/warm old instances and restore services. A legacy/app role that owns the patients table or sequence or can invoke a bypass is a stop. Current tests prove a constrained fixture, not the clinic's actual role graph. Put target setup under an independent maintenance fence with no live writers before any managed transition.
- [ ] Agree on how to start an **unused new series** at the owner's chosen display number (including 1500 if chosen) while protecting P-07000/1 and consumed high-water history. The current synthetic SQL conservatively keeps a single global ordinal at or above 7000. It neither supports nor forbids a smaller starting display value in a new, proven-unused series. Review an independent display offset/series state, collision and re-selection behavior before shipping that choice.

## Gates before exposing settings or cutover

- [ ] With an actual locally signed-in owner, mount only a read-only preview first; apply the exact canonical proof on the same trusted operation/connection and keep legacy permissions unchanged. Preview cannot allocate, write audit mutation rows, change a policy, or reserve any displayed number. Prove existing IDs/files are unchanged and ordinary registration still consumes exactly P-07000 then P-07001.
- [ ] Prove all real managed writers using two actual app processes: manual patient creation, visit open_file, CSV commit, and booking confirmation; maintain existing behavior, export/search/print, race old startup and warm writer against the same DB fence. Rejected older workers must not reseed or allocate, even if already warm. Verify historical file map equality, collision rejection, no reuse on rollback/retired rows, prefix switches, threshold/overflow and retry without a second authority boundary.
- [ ] Mount complete local, normalized identifier classification for the existing data protection boundary before allowing alternate prefixes in outbound clinical text. Prove authoritative lookups include historical files and ambiguous matches. A token that is both a receipt and a patient file is treated as patient. Unavailable or incomplete proof cannot release text. Do not rely on guesswork, trusted input labels, or blanket receipt-prefix exceptions. No expansion of AI scope.
- [ ] Preserve ordinary v1 legacy archives and test active management-grade evidence. It must bind the independent source and approved *different* target, actual archived bytes, the exact standalone decimal counter/flag, policy revision and identity map. Archive data and checksums alone cannot authorize recovery. When any witness is absent or wrong, historical data can remain legacy-compatible but **managed** readiness is held. Exercise actual backup provider/storage/permissions, realistic streaming sizes and no live data exposure. Verify isolated application and native recovery, source remains held, old writers denied, no fallback, and real restored runtime's first new number remains correct. Physical clones that preserve both native identities and hard-crash continuity require separate proof.
- [ ] Separate Save and activation from preview. Only after explicit scope-specific approval, independently reviewed migration/rollback, current CI and staging smoke, bind an idempotent audited owner command to exact target, revision and identity. Neither a review branch, working tests, generic `readyForCutover` from legacy restore, nor a verified optional attachment authorizes launch. Apply staging first if later authorized; this artifact is not a rollout request.

## Rollback and acceptance

If a later activation has already issued a managed number, keep the same fenced allocator or hold issuance. Do not restore unrestricted P allocation, reconstruct the independent sequence from rows, lower high-water or transfer the old owner binding by restore. Preserve current rows and use an independently approved and fenced recovery to resume. Prove the rollback on synthetic data before treating a release as reversible. Never edit past identifiers or move the source as a side effect of checking recovery.

Open findings remain release blockers even if all local cross-lane tests pass. Exact migration checks, mounted owner UX, two process cutoff in the real app, approved recovery, and remote CI are not implied by these synthetic tools.
