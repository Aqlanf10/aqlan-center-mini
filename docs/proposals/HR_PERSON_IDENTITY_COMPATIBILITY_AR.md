## النطاق

- `hr_staff.id` هو الشخص، `users.id` الحساب والفاعل، `parties.id` الطرف المالي. لا دمج بالأسماء، ولا حساب رئيسي مفترض، ولا حذف أو إعادة نسبة للسجلات.
- `identity_revision=0` يقرأ الهوية القديمة؛ بعد التحويل الصريح تقرأ الهوية من الروابط. يظل `user_id` القديم محفوظًا للوصول الحالي، ويرفض محرره القديم التغيير بعد التحويل. الحساب الثاني لا يرث مهامًا خاصة أو أذونات أو عرض رواتب.
- حساب واحد له رابط شخص حالي واحد، والشخص يقبل عدة حسابات. جهة مالية حالية واحدة لكل شخص وشخص واحد لكل جهة. doctor/employee فقط؛ تعارض الحساب أو العقد أو مراجع المسير يرفض الخطة كلها. لا تعديل `users.party_id` أو سياسة عمولة أو أي جهة.
- إنشاء هوية جديدة يعني `unconfirmed/unspecified`، دون تاريخ توظيف أو راتب أو عقد أو استحقاق. لا تغيير لشروط الملفات القديمة. تبقى الهوية غير الموثقة خارج الأهلية التشغيلية والمالية ومنتقي الإسناد.
- خطة خادمية حتمية بمعرفات صريحة، وبصمات مصادر ومخطط وإصدار وسبب ومرجع إثبات. خدمة تطبيق داخلية غير موصولة بمسار HTTP/زر/CLI؛ تعيد التحقق من الجلسة والخطة تحت الأقفال، وترفض stale والتعارض والتكرار. إيصال فريد للطلب والخطة، وأحداث وروابط مؤرخة في المعاملة نفسها.
- تصحيح الرابط يغلقه بدليل ويضيف رابطًا/حدثًا جديدًا؛ لا حذف أو إعادة كتابة تاريخ. المصدر المالي المخالف لا يحسم بأولوية صامتة.
- منع اعتماد الإجازة أو تصحيح الحضور يشمل الشخص عبر الحسابين والمستفيد ومقدم الطلب. الطلب الجديد يحفظ معرف الفاعل ولقطة أدلة الهوية. إغلاق الرابط لاحقًا لا يمحو دليل المنع. الطلب القديم الغامض يحتاج مراجعة؛ لا استنتاج فاعله من اسم عرض.

## التوافق والتفعيل

1. غياب جميع إضافات المخطط يبقي السلوك القديم والمعاينة القرائية متوافقين. ظهور إضافة جزئية يرفض التعامل مع الهوية503؛ لا ensureSchema أو إصلاح تلقائي.
2. المعاينة القديمة تظل READ ONLY وضمن الحدود الحالية، وتقرأ الروابط الصريحة عند وجود المخطط كاملًا وتدرجها في البصمة لكشف stale والتداخل. لا endpoint للتطبيق في هذه الشريحة.
3. تبقى `staffIdForUser` وحراس القراءة والمهام الخاصة وسلطة الحساب كما هي. قارئ هوية جديد لا يستعمل لمنح الوصول. قيود منع الاعتماد يمكنها التضييق فقط.
4. لا تعديل migrations الحالية، أو runtime registration، أو baseline/ownership/schema contract الإنتاجي قبل تخصيص الرقم ومراجعة مستقلة. الاختبارات وحدها تطبق SQL المقترح على قواعد اصطناعية محمية.
5. لا كاتب مالي جديد ولا تفعيل صرف. رابط الجهة يقرأ كتعيين صريح للمراجعة؛ أي ربط بالكاتب المالي القائم لا يتجاوز تعارض الحساب/العقد/الصرف ولا ينشئ جهة بسبب الغياب. الربط السريري للمدير، canonical grants، المالك والتفويض خارج هذه الشريحة.
6. الرجوع إلى كود قديم بعد إدخال هويات جديدة غير مؤكد التوافق؛ لا تفعيل حي قبل تسجيل المخطط وتحديث أدلة backup/restore والتوافق ومراجعة خطة الرجوع.
