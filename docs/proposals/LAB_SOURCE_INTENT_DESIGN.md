# Unified laboratory work intent — design gate, not a release

Base: bounded same-order completion `dac2ea52`. No schema registration, source writer change, deployment or legacy backfill is implied by this document.

## Blocking discovery

`setVisitProcedures` replaces draft `visit_procedures` rows. Their numeric IDs are disposable until signing. Attaching durable prescription-source FKs to those draft IDs, preserving them by heuristic matching, or casually rewriting that existing writer is unsafe: invoice references, pending request replay, inventory and separately composed clinical authorization all need compatible transaction semantics.

## Proposed stable intent

A clinical **work-intent UUID** is an explicit persisted identity independent of disposable execution rows. It is not a hash of tooth/service/price and not the existing display-only group ID.

Proposed, unnumbered schema only after independent review:

- `lab_work_intents`: UUID primary key; patient FK; immutable origin kind and optional original visit FK; explicit group kind (single/bridge/arch/general); initial actor identity; monotonic revision; draft clinical specification and exact member snapshot; optional initial lab-order FK unique across intents; lifecycle/idempotency metadata.
- Draft `visit_procedures` receives nullable `lab_work_intent_id` and explicit member UUID. The payload/read DTO carries both. Delete/reinsert may retain these **explicit identities**, but no durable parent FK depends on the transient numeric procedure ID. An intent's members are not reconstructed by index or clinical similarity.
- `lab_prescription_source_memberships`: order/intent, patient and typed plan-item / final visit-procedure / invoice-item FKs; precisely one source type per link, lifetime uniqueness independent of status. Check exact patient and clinical compatibility transactionally. No unchecked polymorphic key.
- Intent request results are actor-bound, fingerprinted and revision-checked. Same key/same body replays; changed body conflicts. Source commit plus intent/membership must be atomic.

No migration number is chosen here. Reserved clinical migration0073 is a separate authority mechanism, not a work-identity store.

## Source flows

### Visit draft → signing

1. New selected lab work gets an explicit intent/member key in the form. Independent crowns get separate intents even on adjacent/same teeth or at equal price. A bridge is a deliberate group of explicit members and roles.
2. Saving source rows and updating the intent is one transaction. Validate source ownership, expected intent revision, group kind and explicit source-member set. The metadata save remains a draft and creates no monetary entries.
3. The draft writer may replace rows, but carries the explicit intent/member keys. Removed/changed group membership is an explicit draft revision, not silent reassignment. Materialized or dispatched work cannot be repurposed.
4. Signing materializes exact final procedure-ID membership and initial lab order in the sign transaction. The invoice generated by signing aliases those exact procedure IDs. Inventory/clinical authorization/financial behavior is otherwise unchanged.

### Invoice → later execution

- New invoice work uses its generated exact plan item when available; the invoice item links to that same intent/order in the creation transaction.
- Planned execution reuses the exact plan-item alias over every session.
- Truly standalone invoice work retains an immutable invoice-item source until an explicit reviewed later execution link is created. The key is not converted in place. If both sides already own prescriptions, return a conflict for reviewed resolution—never merge/delete automatically.

## Review boundaries that remain unresolved before implementation

- Exact client/server contract for UUID issuance, actor-bound idempotency and expected revisions, including pending-body recovery.
- Where original intent ownership and mutable clinical draft revision live when both invoice and visit contexts can submit concurrently.
- Typed FK validation and uniqueness for explicit bridge members across source kinds; no guessed alias expansion.
- Existing `invoice-revision-db.ts` clinical-lock query lacks a lab-source check. Identity-changing correction/substitution must be blocked until explicit reviewed draft supersession exists. Financial-only correction preserves work identity without duplication or repricing.
- One source lock order: patient/source rows deterministically, then prescription/order; legacy reverse acquisitions fail with NOWAIT conflicts. The clinical authorization candidate holds a lab-table SHARE ROW EXCLUSIVE NOWAIT boundary; integration must respect it.
- Nullable source geometry/full-arch or shade-less work must have an explicit supported contract; incomplete data cannot be auto-filled. Unsupported/ambiguous legacy cases stay review-required.
- Sent specifications are immutable; explicit remake/replacement references predecessor and creates a new generation only through that command, never retry.

## Mandatory acceptance matrix

1. Visit-first→invoice: identical prescription ID/fields, no duplicate.
2. Invoice-first→planned execution: reuse across all sessions.
3. Standalone later explicitly linked; competing existing prescriptions refuse.
4. Explicit three-unit bridge→one request/correct roles; adjacent equal-price independent crowns remain independent.
5. Distinct same-tooth procedures distinguishable; NULL-tooth/full-arch retry-safe where supported.
6. Double-click/lost-response/concurrent visit+invoice save/sign→one identity, initial order, dispatch event.
7. Rollback of source transaction leaves no orphan invoice/prescription.
8. Correction/sign/reassignment/dispatch races serialize or recoverably conflict; no deadlock/partial state.
9. Cancellation does not release source identity or resurrect on retry; explicit remake preserves predecessor.
10. Financial correction never duplicates work; service substitution cannot rewrite dispatched specifications.
11. Reject cross-patient IDs, mixed groups, unassigned doctor, accountant, revoked role/session and inactive lab server-side.
12. Save/dispatch preserves monetary rows, principal, currency, financial doctor attribution and payables.
13. Preview/print agree on explicit teeth/roles/sent snapshot; incomplete drafts visibly incomplete.

Legacy orders remain same-ID completion with unknown lineage. No best-effort backfill from visit/tooth/type/free text, and no silent merging of historical duplicate orders.

## Implemented local slice and deliberate limits (2026-10-25)

This uncommitted child branch adds explicit source fields and draft UUIDs, exact-key/hash receipts, and source mutation guards. It is not published or registered as a migration. Only the owned synthetic PostgreSQL18 instance may apply the proposal for tests.

Visit reload persistence contains only actor/patient/visit-scoped request identity and SHA-256 hash. No clinical note, prescription body, or new PHI journal is persisted. Same-session retry retains the exact sealed body in memory. Reload reconciles a committed server receipt; if no committed result is found and the sealed body is unavailable, writes remain blocked rather than regenerating identity. This limitation is intentional pending a separate privacy decision.

Current supported grouping is explicit single-tooth or bridge membership. Full-arch/null-tooth work, automatic legacy lineage recovery, post-materialization membership change, and standalone invoice execution linkage without exact proof remain blocked. Form grouping joins only new revision-zero groups. Template-generated invoice capture and invoice retirement commands remain disabled. Existing source-linked orders open the same canonical completion editor rather than creating another order.

An exact replay locks and revalidates the current visit patient before returning. Visit relinking/deletion also protects durable command provenance even when a command contains no active members. Legacy `(visit,tooth)` order uniqueness must remain effective for legacy rows while explicit work uses a unique intent key; the proposal and dedicated PostgreSQL tests own this boundary.

No release claim follows from unit tests: integrated real-PostgreSQL source writers, races and all relevant acceptance rows above, plus hosted responsive preview/print evidence, remain required.
