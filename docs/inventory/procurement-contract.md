# Procurement checkpoint and ownership contract

Base 148fcbeac229cb279848e6ea37049d1599a4fafe; independent inventory branch. Runtime document code is new and cohesive. `schema-proposal.ts` is additive and unnumbered; it is explicitly applied only in isolated synthetic fixtures. No shared migration/schema registry is modified. No live/staging publication has occurred.

## Actual implemented boundaries

- `quantities.ts`: strict decimal quantities against NUMERIC(12,3), item-specific immutable conversion/version snapshots, rejection of inexact conversion/zero/overflow. A package factor is never inferred from text.
- `procurement.ts`: content/version-bound full/partial approval, fixed currency approval valuations, cumulative approved-source order budgets/quantities, versioned purchase-order amendments (`planOrderAmendment`, preserving immutable historical monetary/FX commitments and delta allocations across repricing, shipping, discount, and FX rounding, and forbidding weakening of `trackLot`, `requiresExpiry`, `minimumShelfLifeDays`, or unit conversions on existing lines), inspected receipt classification with explicit excess-arrival decisions (`return_excess_to_supplier`, `hold_for_order_amendment`), quarantine resolution (`release`, `reject_return`, `dispose` with `disposedBaseQuantity` and `disposedExcessBaseQuantity` tracked separately so disposing held unapproved excess never invalidates receipt history for subsequent multi-line receipts), exact three-way quantity/price match, shipping/discount apportionment and canonical payload identity. A domain plan is not a database commitment.
- `procurement-store.ts`: trusted actor re-read from users; single existing clinic scope; configured approval policy with no implicit limit; approved requests locked in sorted order; supplier active/kind checks; immutable registered package versions; transaction-level idempotency; order/receipt locks; append-only versioned order amendments (`amendPurchaseOrder`, inserting newly added immutable `purchase_order_lines` before `purchase_order_source_allocations` within the same transaction); accepted/quarantined/rejected/disposed classification; quarantine release blocked with `order_amendment_required` when excess arrival is held pending PO amendment; stock inserted into existing `inventory_movements` without supplier debt; true lots/locations referencing those movements; existing `insertAuditRow` with `sanitizeInventoryAuditDetails` in the same transaction. Audit failure rolls back stock and document effects. Identical retries return original result; changed content conflicts.
- Supplier invoice matching is persisted and reserves matched accepted quantities. It creates no payable or cash. `supplier_invoice_payable_links` is an append-only unique invoice→existing payable relation for the root-owned finance adapter. Existing `inventory_movements_payable_uniq` is not changed. No supplier order is sent.
- New command API rejects arbitrary status patches. Management commands (`request.revise`, `request.approve`, `order.issue`, `order.amend`, `receipt.post`, `quarantine.resolve`, `invoice.match`, `legacy.reconcile`, `custody.dispatch`, `custody.approve_waste`, `custody.propose_settlement`) are admin-only; requesters (`request.submit`) are admin/reception/doctor on this pinned base; doctor/admin custody commands (`custody.acknowledge`, `custody.consume`, `custody.return_to_store`, `custody.stocktake`, `custody.close_package`, `custody.object_settlement`) enforce transaction-level doctor party and clinical ownership. Actor and clinic scope come from server validation; `requestedBy` in client JSON is overwritten from authenticated identity.
- Owned bilingual (`ar`/`en`) UI workspaces cover `/inventory/procurement` (requester), `/inventory/procurement/review` (administration monetary revision, partial approval, and print), `/inventory/procurement/operations` (approved-source orders, receipts, excess-arrival decisions, quarantine resolution, historical reconciliation, three-way invoice match, and prints), and `/inventory/custody` (transfers, clinical consumption, waste approval, return to store, stocktake, package closure, and annual settlement review). Broader delegated capabilities and shared finance/clinical writer integrations remain deferred.

## Quantities, money and audit ownership

`inventory_movements` is the clinic quantity source. Lot/location allocations reference it; there is no editable stored balance. Custody transfers must conserve clinic stock/value and never count as consumption. `payables`/`expenses`/payment allocations remain debt/cash sources. Receipt is not invoice and invoice is not payment. Doctor attribution is contractual consumed cost, not purchased/transferred stock. Applied material deductions net linked reversals determine `D`; theoretical `materialRate` is not substituted. No implicit payroll deduction or disciplinary debt.

The 29-table schema proposal (`schema-proposal.ts` + `custody-schema-proposal.ts`) includes immutable unit versions, locations and approval policies; request headers/revisions/lines/approval events; orders/lines/source allocations; receipts/lines; stock lots/movement allocations/quarantine dispositions; supplier invoice match documents/receipt allocations/payable links; operation identities; custody transfers/lines/acknowledgements/ack lines; and custody waste approvals, usage events, stocktakes, package closures, annual settlements, and settlement objections. It adds guards only to these new evidence tables and never removes existing guards. Existing `audit_log` and `insertAuditRow` are reused with sensitive-token redaction (`sanitizeInventoryAuditDetails`).
