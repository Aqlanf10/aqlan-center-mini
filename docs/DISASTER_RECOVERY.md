# التعافي من الكوارث والنسخ الاحتياطي (P1.16)

> **الحالة:** P1 — البنية والتوثيق والتحقق مؤسَّسة ومُختبرة على بيئات معزولة.
> **لا نسخ مجدولة يعمل في الإنتاج بعد** — كل الأرقام أدناه أهدافٌ مقترحة (target)
> لا ضمانات موثَّقة، حتى تُفعَّل الجدولة وتُثبَت بتمرين فصلي موثَّق.

## ما الذي يُنسخ (وما لا يُنسخ)

| المكوّن | يُنسخ؟ | الآلية |
|---|---|---|
| قاعدة البيانات (كل الجداول + العدّادات) | ✅ | تصدير SQL تنسيقي داخل معاملة `REPEATABLE READ READ ONLY` (لقطة متسقة) |
| مستندات المرضى (الأشعة/التقارير) | ✅ | تُحقَّن بصمة+مقاسًا لكل ملف، والفشل يُفشل النسخة كلها |
| المفتاح (manifest) | ✅ | `manifest.json` **آخر مدخل** — شهادة اكتمال التنزيل |
| التهيئة (متغيرات البيئة) | ❌ | مسؤولية المشغّل: `DATABASE_URL`، `SESSION_SECRET`، `DOCUMENTS_DIR`، `PGSSL_ROOT_CERT`، `CLINIC_TIME_ZONE` — تُوثَّق خارج المستودع (بلا أسرار في git أبدًا) |
| أسرار مزودي AI | ضمن القاعدة | مشفَّرة بـ`SESSION_SECRET` (secretbox) — **نسخها بلا نسخ SESSION_SECRET بلا فائدة**: يجب الحفاظ على قيمة `SESSION_SECRET` نفسها عبر الكوارث |

## الصيغ المتاحة

1. **نسخة كاملة بملف واحد** (الموصى بها): `database.sql` + `documents/` + `manifest.json`
   داخل `tar.gz` واحد — تنزيلها من لوحة الأدمن («النسخة الكاملة»). كل مستند
   يُتحقَّق منه عند الإنشاء.
2. **نسخة SQL وحدها** (منزوعة المستندات) — تصدير نصي.
3. `scripts/backup.mjs` — `pg_dump` خارجي (صيغة custom) — أداة مشغّل متقدمة.

## التكرار والاحتفاظ (مستهدف — غير مُفعَّل)

| البند | الهدف المقترح |
|---|---|
| تكرار النسخ الكاملة | **يوميًّا** (تنزيل يدوي حاليًّا حتى تُفعَّل الجدولة) |
| تكرار إضافي (WAL/PITR) | **مرحلة P2** — يتطلب خطة Railway المناسبة |
| الاحتفاظ | 7 نسخ يومية + 4 أسبوعية + 6 شهرية، خارج الموقع (تنزيل للتخزين البارد) |
| RPO (الهدف) | **24 ساعة** مع النسخ اليومي اليدوي؛ **≤15 دقيقة** عند تفعيل PITR في P2 |
| RTO (الهدف) | **≤2 ساعة** من أرشيف كامل جاهز التحقق (الإثبات الحالي للتدريب: دقائق) |

> ⚠️ لا نادّعي أرقامًا غير قابلة للتحقق: هذه **أهداف**. RPO فعلي اليوم = عمر أحدث
> نسخة نزّلها الأدمن. أول خطوة تشغيلية بعد اعتماد P1: تفعيل تنزيل مجدول
> (cron خارجي أو workflow) مع فحص `verify:backup` بعد كل تنزيل.

## الإجراء: التحقق قبل أي استعادة (P1.12)

**الأرشيف يُقرأ ويُحقَّق كاملًا قبل لمس أي قاعدة هدف.** العشرة تحققات:

1. قراءة الأرشيف كاملًا (كشف البتر بعلامة نهاية TAR).
2. البنية: `database.sql` موجود و`manifest.json` موجود **وآخر مدخل**.
3. المفتاح سليم البنية (الصيغة، الإصدار، الحقول).
4. بصمة SHA-256 لملف SQL تطابق المفتاح.
5. بصمة كل مستند تطابق المفتاح.
6. مقاس كل مستند يطابق المفتاح.
7. مسارات نسبية سليمة (لا مطلق، لا `..`، لا null byte).
8. رفض path traversal بالحل داخل الأساس (لا `startsWith`).
9. كشف الوجهات المكررة بعد التطبيع.
10. كل ملف مذكور في المفتاح موجود في الأرشيف.

**أي فشل ⇒ لا استعادة قاعدة أصلًا.** (الأمر: `npm run restore:full -- الأرشيف.tar.gz`
بعد ضبط `DATABASE_URL` على هدف فارغ و`DOCUMENTS_DIR` على دليل staging.)

**(P1-FIX-8) بوابة تصنيف الهدف قبل أي اتصال:** `restore:full` يرفض بنيويًّا الأهداف
المصنَّفة `production` والأهداف البعيدة غير المصنَّفة (`unknown-remote`) مهما كانت
بيئة جهاز التشغيل — التصنيف بـ`DATABASE_ENVIRONMENT=test|development|staging|production`
الصريح (القاعدة المخصصة للاختبار/التدريج تُصنَّف قبل التشغيل). لا علم يتجاوز هذا
في P1، والاستعادة إلى الإنتاج نفسها قرار ما بعد الاعتماد بمسار منفصل مصرَّح ومدقَّق.

## الإجراء: الاستعادة بإعداد Staging/Cutover (P1.15)

النمط الممنوع: «استُعيدت القاعدة وفشلت المستندات» — عيادة تعمل بسجلات بلا أشعة.
النمط المطبَّق:

```
تحقق كامل من الأرشيف (١–١٠ أعلاه)
  → استعادة القاعدة إلى هدف معزول فارغ (قاعدة اختبارية/مؤقتة — ليس الإنتاج)
  → المخطط من نظام الهجرات (0001: DDL خالص بلا بذور)
  → البيانات من SQL النسخة (باستبعاد صفوف تسجيل الهجرات نفسها)
  → المستندات إلى دليل staging معزول + تحقق بصمة ما بعد الكتابة
  → تحقق الهدف (فحص حرج + اتساق هجرات + جداول)
  → READY FOR CUTOVER (مع خطوات التبديل موثَّقة — لا تُنفَّذ آليًّا)
```

**خطوات التبديل إلى الإنتاج (توثيق فقط — قرار بشري بعد مراجعة مستقلة):**

1. أوقف تطبيق الإنتاج (Railway: إيقاف الخدمة) حتى لا تُكتب بيانات أثناء التبديل.
2. خذ نسخة احتياطية من قاعدة الإنتاج الحالية قبل أي تبديل (خطة رجوع).
3. استبدل قاعدة الإنتاج بالهدف المعزول المُستعاد.
4. انقل محتوى دليل staging إلى `DOCUMENTS_DIR` النهائي.
5. أعد تشغيل التطبيق وشغّل `npm run db:status` — يجب أن يظهر `consistent`.
6. تحقق بصريًا: عدد المرضى، آخر الدفعات، عينة أشعة تُفتح من ملفاتها.
7. وثّق التبديل في سجل الحوادث مع SHA الأرشيف وطابع الزمن ومن أذن به.

## التحقق من الاستعادة (تمرين مُثبت آليًّا)

`__tests__/postgres/restore-drill.test.ts` (على PostgreSQL حقيقي، معزول، يُدمَّر
ويعاد بناؤه داخل الاختبار نفسه) يتحقق بعد الاستعادة من:

- عدد المرضى/المواعيد/الفواتير/بنودها/الوصفات/المستندات/الورديات.
- الأحداث المالية: المبالغ، العملات، سعر الصرف المسجَّل لحظة الدفع، المكافئ الأساسي،
  مفتاح الإعادة، وعلاقة الردّ بالسند الأصلي.
- WAC: نفس الكمية والقيمة والمتوسط قبل الاستعادة وبعدها.
- **العدّادات التسلسلية**: إدخال مريض ووصفة جديدة بعد الاستعادة لا يصطدم
  بمعرّفات قديمة (setval فوق MAX).
- المستندات: العدد، البصمة، المقاس، وتطابق البايتات.
- الأرشيف الفاسد (بصمة/بتر) ⇒ **لا جداول أُنشئت أصلًا في الهدف**.

> التمرين كشف وأصلح ثلاثة أعطاب كامنة في النظام القديم (موثَّقة في
> PRODUCTION_HARDENING_REPORT.md): مستندات النسخة الكاملة لم تكن قابلة
> للاستعادة أصلًا، وأعمدة المصفوفات تُفشل الاستعادة، وreset العدّادات
> يتعثر على المفاتيح النصّية.

## من يملك بدء الاستعادة؟

- **الأدمن** (المالك) حصرًا: تنزيل النسخ، وتشغيل أمر الاستعادة، وقرار التبديل.
- الاستعادة إلى الإنتاج تتطلب موافقة المالك الموثَّقة (خطوات ١–٧ أعلاه).
- في P1: **لم تُنفَّذ أي استعادة على أي بيئة غير معزولة، ولا Production Cutover.**

## خطة الرجوع

التبديل قابل للرجوع لأنه لا يهدم شيئًا: قاعدة الإنتاج القديمة تبقى كما هي حتى
يتحقق المشغّل من الجديدة (خطوة ٥–٦). الرجوع = إعادة توجيه التطبيق إلى القاعدة
القديمة ودليل المستندات القديم — ولذلك خطوة ٢ (نسخة قبل التبديل) إلزامية.
