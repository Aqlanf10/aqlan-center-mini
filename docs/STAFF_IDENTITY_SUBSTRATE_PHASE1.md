# Reconstructed identity substrate — phase 1, NOT activation

This is new reconstruction from recovered composition `86c98ef34cba5e01badfc0ba7777ce22cd4b4002`, not recovered source equivalent to the lost canonical runtime. It is an unregistered, quarantine-only storage proposal. No application route imports it, no migration registry installs it, and no account, owner, grant or credential is issued.

## Trust boundary

Every result explicitly has `authorizesSessions: false`. Neither a subject UUID nor a successful catalogue probe is authorization. There is no active transition. Frozen 0076 control state cannot override the independent mandatory identity quarantine. Existing v10 identity tables/subject column are rejected, not silently migrated. No legacy owner bridge, role-derived ownership, or imported credentials establish target continuity.

Subjects and target generations are minted inside the server lifecycle functions. This is the service API guarantee, not cryptographic issuance enforced against a privileged SQL writer: UUID columns themselves accept SQL values. Callers supply only the observed generation/revision and exact prior binding for compare-and-swap. Historical subject rows have no foreign key to mutable users: retirement permits later account deletion, but immutable identity tombstones survive numeric-ID reuse. Current bindings have a restrictive user FK. Rebinding always creates a fresh subject; A → B → A cannot reuse A's prior subject.

Individual quarantine retirement/rebinding advances registry revision, not target generation; each replacement mints a new subject. Future session admission must verify current subject binding and credential/permission revision, not merely generation.

Generation advancement appends target history and moves only the current target head. It neither rewrites original subject provenance nor silently rebinds accounts. Existing bindings remain quarantined. A generation with reason `restore` is not permission to run an application restore.

## Transaction protocol

The caller owns an explicit READ COMMITTED transaction and rollback on any error. Fixed order: substrate advisory fence, strict catalogue inspection, frozen control row, current identity-state row, affected account/binding, then any future domain locks. Mutations use generation + registry-revision CAS and binding changes also exact old-subject CAS. Functions check XID at entry and exit. They return no reusable transaction capability and own no BEGIN/COMMIT. Savepoint rollback rolls back identity changes too.

SQL guards enforce local immutable-row and transition shape. Complete subject → creation-event and latest-event ↔ current-binding cycles, per-user previous-subject event chains, and exact revision accounting (generation count + binding-event count) are checked by every lifecycle read/write, not a deferred SQL completeness constraint. An intentionally incomplete privileged SQL transaction can commit, but subsequent service entry refuses it without repair/adoption. Adversarial tests commit both orphan subjects and missing-current cycles and prove refusal.

Concurrent callers serialize before reading current state; only one caller with the same expected revision succeeds. An account must be explicitly retired before deletion; registry history cannot cascade away.

## Verification and limitations

Fresh owned PostgreSQL 18.6 test suite covers initialization, no legacy account/control mutation, binding/stale CAS, savepoint rollback, retirement/delete/reuse, target generation provenance, autocommit/isolation refusal, client transaction reuse, concurrent contenders, schema drift/function/trigger corruption and all-source restore refusal. Test schemas use unique `aqlan_identity_` prefixes and cleanup only their own schemas.

This phase does not implement signed session validation, opaque operation admission, permissions administration, login/proxy/UI, inventory capability integration, owner preparation, or complete restore acceptance. Those cannot be inferred from passing substrate tests.
