# تجهيز تسجيل مخطط هوية الموظفين

الأساس: `6090722977a37981ddf56585c180f782b5a5249b`، بعد دمج PR341.
فرع واحد وDraft PR واحد. لا نشر ولا تطبيق على قاعدة حية ولا تشغيل لأداة تحويل الهوية من HTTP أو UI أو CLI أو startup.

## حدود التسجيل

- سلسلة main تحتوي 56 ملفًا وأعلى رقم `0061`. `0062` مرشح غير محجوز؛ لا ننشئ ملف هجرة مرقمًا قبل تأكيد الجذر.
- وجود المخطط يغير defaults ويفعّل أدلة الطلبات وحراس الاعتماد. ليس تغييرًا خاملًا، حتى مع بقاء أداة تحويل الروابط داخلية بلا نقطة استدعاء تشغيلية.
- الاختبارات المستقلة تستخدم اقتراح SQL غير المرقم داخل قواعد PostgreSQL اصطناعية مملوكة للاختبار. سجل الهجرة الاصطناعي ذو اسم غير رقمي لا يدخل مجلد migrations ولا يحجز رقمًا.
- تسجيل حقيقي لاحق يحتاج ملفًا مرقمًا محجوزًا ونسخة runtime مطابقة بايتًا، وفحص checksum تحت القفل المشترك، وتحديث عقد المخطط وملكية الجداول ومراجعة مستقلة.

## الملفات المشتركة المعلنة قبل تعديلها

- `lib/clinic-reset.ts`: تصنيف جداول الهوية الأربعة ضمن KEEP، مع إثبات reset محلي يحفظها.
- `lib/migrations.ts` وموضع HR في `lib/db.ts`: فحص المصدر والتسجيل والتزامن والرجوع الذري؛ لا توصيل هجرة جديدة قبل الحجز.
- مسار النسخ في `lib/db.ts` و`lib/backup.ts` ومسارا استعادة SQL والأرشيف: تغيير محدود فقط عند إثبات خلل باختبار، مع استمرار حراس قاعدة البيانات.
- الاقتراح غير المرقم وعقد تعريفاته: أي تصحيح يستلزم مقارنة تعريفات جديدة ومراجعة البصمة، بلا تعديل هجرة منشورة.

## أدلة الشريحة المطلوبة

1. ترقية main، حسابات legacy والطلبات القديمة المعلقة، ثم startup متكرر بلا تحويل أو منح صلاحيات.
2. تزامن migrator/runtime، checksum فاشل، SQL يفشل في المنتصف، ومخطط جزئي غير مسجل؛ لا قبول تلقائي أو تسجيل كاذب.
3. SQL restore وfull archive restore إلى هدفين معزولين قبل تحويل اصطناعي وبعد تحويل وتصحيح، مع التاريخ والمعرفات والتسلسلات وإعادة الإيصال.
4. حفظ جداول الهوية خلال reset اصطناعي، والحراس مفعّلة طوال الاستعادة.
5. قياس أقفال DDL وأزمنة الانتظار وحدود lock_timeout/statement_timeout وتوثيق إصدار رجوع متوافق مع المخطط؛ لا down migration تحذف التاريخ.

لا اختيار لروابط أشخاص حقيقيين أو صلاحياتهم، ولا صرف أو دين، ولا عمل في المخزون أو التقويم أو بيئة Staging.

## نتائج مستقلة عن رقم الهجرة

- كشف اختبارا SQL والأرشيف فشل استعادة رابط حساب مغلق بعد إسناد الحساب إلى ملف legacy آخر. التصحيح يقصر حجز الحساب على الروابط الحالية؛ الرابط المغلق يحتاج حدثي فتح وإغلاق مطابقين. إدراج إغلاق مزيف أو إعادة فتح رابط متعارض ما زال مرفوضًا.
- انطبق الخلل نفسه على جهة مالية أُغلق رابطها قبل تغيير نوعها. نوع الجهة الحالي يحكم الرابط الحالي، والتاريخ المغلق يثبت بأحداثه. لا تعطيل للحراس في أي مسار استعادة.
- النسخة كانت تعيد التسلسل إلى MAX(id)، فتفقد الأرقام المستهلكة في عمليات فاشلة وحالة `is_called`. أصبحت تحفظ حالة التسلسلات التابعة لأعمدة id بعد قراءة الصفوف؛ تعالج معرّفات مستوردة أعلى من التسلسل دون إعادة عدّاد إلى قيمة تصطدم بالبيانات. قيم BIGINT تبقى نصوصًا عشرية بلا تقريب JavaScript. التسلسلات ليست MVCC؛ هذه قراءة لاحقة لحالتها، وليست وعدًا بلقطة زمنية ذرية لجميع العدادات.
- صار migrator يتحقق من نصوص جميع الملفات وبصماتها ومن أسماء صفوف التسجيل وحالة اعتمادها قبل أول تغيير. runtime كان يتحقق من النصوص أصلًا. لا اعتماد تلقائي لمخطط جزئي موجود.
- KEEP يشمل جداول الهوية الأربعة. أثبت reset محلي حفظ صفوف الهوية وحالتها والتاريخ وإعادة الإيصالات بعد أخذ نسخة، دون حذف نسخ قائمة.

## التوافق والتفعيل والرجوع

الاختبارات تنشئ قاعدة من سلسلة main ثم ترقي الاقتراح، أو تستعيد نسخة main قديمة إلى مخطط الاقتراح. تبقى قيم الموظفين القديمة والحسابات وصلاحياتها وطلبات الإجازة وتصحيح الحضور المعلقة كما هي؛ أعمدة دليل الهوية القديمة تبقى NULL. يرفض اعتماد الشخص لطلبه. المراجع الذي له هوية عمل معروفة يتوقف بـ409 أمام طلب قديم غير موثق، بينما تبقى المراجعة المستقلة غير المرتبطة خاضعة للحراس القائمة. لا اختراع لهوية مقدم الطلب من الاسم.

وجود المخطط يبدّل default الملف الجديد إلى `unconfirmed/unspecified` ويفعّل الأدلة والحراس حتى بلا تحويل. لا endpoint جديد ولا تطبيق روابط من startup أو CLI. لا تعديل عقد أو راتب أو عمولة أو دفع ضمن هذه الشريحة.

startup الحالي، بما فيه seed المعتاد، يحفظ كل الصفوف وهوية الموظفين بعد الترقية وبعد التصحيح. محاولات `ON CONFLICT` القائمة تستهلك بعض تسلسلات الإعدادات المرجعية؛ هذا سلوك سابق وليس تحويل موظفين. لم نعدّل تلك المسارات.

**main609/PR341 ليس إصدار رجوع كاملًا للتعريف المصحح**: تجربة مستقلة استدعت قارئ PR341 الفعلي على قاعدة اصطناعية بالتعريف الجديد ورفض بـ503 كما ينبغي للعقد الثابت. قبل تسجيل المخطط وتفعيله يلزم إصدار توافق يتضمن عقد الحراس والتصحيحات الحالية؛ رأس هذه الشريحة بعد نجاح المراجعة هو المرشح لذلك الإصدار. الرجوع يكون للكود المتوافق مع إبقاء المخطط والتاريخ، وليس حذف الجداول أو الأدلة. لا تطبيق حي في هذه المهمة.

## الأقفال والمهلات وحدود القياس

- ALTER TABLE في الاقتراح يأخذ ACCESS EXCLUSIVE على hr_staff وجدولي الطلبات. تغيير CHECK قد يفحص الصفوف الموجودة؛ الاختبارات الاصطناعية الصغيرة لا تقدّر زمن إنتاج أو حجم بياناته.
- migrator وruntime يستخدمان قفل advisory نفسه، ثم معاملة مستقلة للهجرة وتسجيلها. اختبار بعميلين متنافسين أثبت انتظار الاثنين ثم تسجيل مرة واحدة، والتشغيل التالي بلا كتابة.
- اختبارات اتصال بـ`lock_timeout=150ms` و`statement_timeout=2000ms` تلغي انتظار قفل الجدول أو القفل advisory قبل أي ترقية جزئية. واختبار `statement_timeout=150ms` مع SQL متعمد البطء أثبت rollback وتحرير القفل. هذه حدود fixture، وليست إعدادًا إنتاجيًا اختير خفية.
- pool التطبيق يضبط `statement_timeout=60000` حاليًا؛ CLI migrator لا يضع حدًا صريحًا للانتظار. عند تسجيل الهجرة لاحقًا يلزم وضع حدود اتصال مراجعة **قبل** انتظار القفل advisory، ثم حدود DDL داخل المعاملة. `SET LOCAL` داخل ملف SQL وحده لا يحمي الانتظار السابق له. لم نغيّر مهلات كل الهجرات القديمة ضمن التحضير.
- تصادم مخطط جزئي غير مسجل أو SQL فاشل يرجع تغييرات الهجرة ولا يكتب إيصال تسجيل. فشل الاستعادة يعني التخلص من الهدف الاصطناعي المعزول أو إعادة تهيئته بصورة معلنة؛ PostgreSQL لا يرجع `setval` كصفوف المعاملة، فلا يُقدَّم الهدف الفاشل كجاهز.

## حدود دليل الاستعادة

نُفّذ `scripts/restore.mjs` الفعلي و`stagedRestore` الفعلي. يشير اسم الأخير إلى هدف استعادة محلي معزول، ولا علاقة له ببيئة Railway Staging المتوقفة. لا ترحيل فوق قاعدة حية ولا حذف backups. في اختبار الأرشيف فقط استُبدل اكتشاف ملفات الهجرة لإلحاق الاقتراح غير المرقم؛ لم يُستبدل المهاجر أو SQL أو الحراس. لذلك لا ندّعي نجاح نشر أو مسار هجرة مرقمة لم تُنشأ بعد.

بقي قبل التسجيل: تأكيد الحجز، الملف المرقم وruntime bundle المطابق، فحص ما قبل/بعد التسجيل وتعريفاته تحت القفل، تحديث عقود schema/ownership، إعادة اختبارات المسار الحقيقي بلا استبدال اكتشاف الملفات، مراجعة مستقلة وإصدار توافق للرجوع. لا دمج أو نشر ذاتي من هذا الفرع.
