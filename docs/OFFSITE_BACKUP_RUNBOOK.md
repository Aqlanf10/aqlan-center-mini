# النسخ الاحتياطي خارج منصة الاستضافة — دليل التفعيل وتجربة الاستعادة المشهودة (P0-3)

> لمن: مالك المركز أو من يفوّضه. لا يتطلب برمجة.
> ما يفعله النظام: كل نسخةٍ تُبنى وتُتحقق منها على القرص الدائم تُشفَّر (AES-256-GCM)
> وتُرفع إلى حاويةٍ عندك في Cloudflare R2 أو Backblaze B2، ثم يُفحص حجمها هناك. إن
> ضاعت منصة الاستضافة نفسها بقيت النسخة عندك، ولا يقرؤها أحدٌ بلا مفتاح التشفير.

## ١) أنشئ الحاوية ومفاتيحها (مرة واحدة)

**Cloudflare R2** (مجاني حتى 10GB):
1. من لوحة Cloudflare: R2 ← Create bucket ← اسمٌ مثل `aqlan-clinic-backups`.
2. R2 ← Manage R2 API Tokens ← Create API Token بصلاحية **Object Read & Write** على
   هذه الحاوية وحدها.
3. انسخ: Access Key ID، وSecret Access Key، ورابط S3 API
   (`https://<account-id>.r2.cloudflarestorage.com`).

**أو Backblaze B2:** Buckets ← Create a Bucket (Private) ← Application Keys ← Add a New
Application Key مقيّدٌ بالحاوية. الرابط `https://s3.<region>.backblazeb2.com` والمنطقة
مثل `us-west-004`.

## ٢) أنشئ مفتاح التشفير (مرة واحدة — واحفظه في مكانين آمنين)

المفتاح 64 خانة hex. أنشئه على أي جهاز:

```bash
openssl rand -hex 32
```

**احفظه خارج المنصة وخارج الحاوية** (مدير كلمات مرور + ورقة في خزنة). بلا هذا
المفتاح لا تُفكّ أي نسخة — وهذا مقصود: من يسرق الحاوية لا يقرأ شيئًا.

## ٣) ضع القيم في بيئة الخادم (Railway ← الخدمة ← Variables)

| المتغير | القيمة |
|---|---|
| `BACKUP_S3_ENDPOINT` | رابط S3 API من الخطوة ١ |
| `BACKUP_S3_BUCKET` | اسم الحاوية |
| `BACKUP_S3_ACCESS_KEY_ID` | Access Key ID |
| `BACKUP_S3_SECRET_ACCESS_KEY` | Secret Access Key |
| `BACKUP_S3_REGION` | `auto` لـR2، أو منطقة B2 |
| `BACKUP_ENCRYPTION_KEY` | المفتاح من الخطوة ٢ |

ثم من البرنامج: **الإعدادات ← النسخ الاحتياطي ← «الوجهة: تخزين خارجي (R2 / Backblaze)»**
← تفعيل، مع سببٍ مكتوب. تظهر الوجهة «موصولة بالحاوية …» إن كانت القيم كاملة، وإلا
تسمّي المتغيرات الناقصة بأسمائها (لا بقيمها).

## ٤) تحقق من أول نسخة

«نسخ الآن» من شاشة النسخ، أو انتظر النسخة المجدولة. في سجل النسخة يجب أن تظهر
الوجهة `s3` بحالة **نجحت** وحالة التكرار **complete**. وفي الحاوية ملفٌ تحت
`aqlan-backups/…tar.gz.enc`.

## ٥) تجربة الاستعادة المشهودة (شرط الاعتماد — تُعاد كل ثلاثة أشهر)

تُجرى على **قاعدة فارغة معزولة** لا على الإنتاج أبدًا — الأداة ترفض أي هدفٍ مصنَّف
إنتاجًا قبل أن تتصل به. يحضرها شاهد (غير المنفِّذ) يوقّع على التقرير.

```bash
DATABASE_URL=postgres://…/drill_empty_db   # قاعدة فارغة جديدة للتجربة
BACKUP_S3_ENDPOINT=… BACKUP_S3_BUCKET=… BACKUP_S3_ACCESS_KEY_ID=… BACKUP_S3_SECRET_ACCESS_KEY=… BACKUP_S3_REGION=auto \
BACKUP_ENCRYPTION_KEY=…                    # من مكان حفظه الآمن — لا من Railway
  npm run backup:drill -- --witness "اسم الشاهد" --operator "اسم المنفِّذ" --staging-dir ./drill-documents
```

`--staging-dir` مجلدٌ **فارغ ومنفصل** تُكتب فيه مستندات النسخة. الأداة ترفضه إن كان
مجلد المستندات الحيّ (`DOCUMENTS_DIR`) أو داخله أو حاويًا له، أو كان فيه ملفات — فلا
تُكتب التجربة فوق أشعة المرضى الحقيقية مهما كانت بيئة الجهاز.

ما تتحقق منه الأداة قبل أي لمس:
1. بصمة الملف المنزَّل = بصمته عند الرفع (لم يتلف ولم يُعبث به).
2. المفتاح المعطى هو مفتاح النسخة (بصمة المفتاح مطابقة).
3. فكّ التشفير ينجح وبصمة الأرشيف المفكوك = بصمته عند النسخ.

ثم تستعيد بالمسار الموثَّق نفسه (`restore:full`: التحققات العشر، والمستندات إلى
staging)، وتطبع تقريرًا عربيًّا وتحفظه `restore-drill-<الوقت>.json`. **التجربة ناجحة**
حين يقول التقرير «نجحت ✔» وتظهر الجداول والفحص الحرج سليمًا. افتح القاعدة المستعادة
وابحث عن مريضين أو ثلاثة تعرفهم — ثم يوقّع الشاهد على نسخة مطبوعة من التقرير وتُحفظ.

## ما لا يفعله النظام (صراحة)

- لا يستعيد إلى الإنتاج أبدًا — الانتقال إلى نسخة مستعادة قرارٌ تشغيلي موثَّق خطواته
  في `docs/DISASTER_RECOVERY.md`.
- لا يحذف النسخ القديمة من الحاوية: اضبط «Lifecycle rule» في الحاوية (مثلًا حذف ما
  أقدم من 90 يومًا) من لوحة المزوّد.
- لا يُخزّن المفاتيح في قاعدة البيانات ولا يطبعها في أي سجل.
