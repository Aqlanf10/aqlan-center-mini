# عقد استعادة نتيجة الحجز المباشر المصنّف — P1، للمراجعة قبل الكود

التاريخ: 2026-11-02. **منفّذ في Source Draft غير منشور، ولم تجتز اختبارات PostgreSQL الحقيقية بعد.** لا يغيّر حجز legacy الذي يغيب عنه `appointmentPurpose`، ولا يخص دفع رسم المعاينة. ينطبق فقط على الحجز المباشر المصنّف `consultation` / `start_treatment`؛ 0095 محجوزة وغير منشورة.

## السبب

`POST /api/appointments` الحالي يحفظ الموعد وصف provenance وaudit في معاملة، ثم يعيد `201`. انقطاع HTTP بعد COMMIT يجعل النتيجة مجهولة للمتصفح، ولا يثبت تطابق مريض/تاريخ/وقت أنه *نفس الأمر*. إرسال أمر ثانٍ دون هوية قد يصنع موعدًا ثانيًا. `booking_requests` الموجود يخص مسارًا آخر ولا يُستعار كسند للحجز المباشر.

## عقد الأمر والصف

1. يُنشئ المتصفح `commandId` بصيغة UUID مرة لكل نقرة حجز مقصودة، ويحفظه حتى الحكم النهائي. أي timeout أو انقطاع لا يولّد UUID آخر ولا يُظهر «فشل الحجز» على أنه مؤكد.
2. صف `appointment_purpose_provenance` الواحد يحمل للحجز المباشر فقط `command_id UUID UNIQUE NOT NULL` و`command_hash` SHA-256 للاختيار المطبّع و`actor_user_id` الثابت، إلى جانب `recorded_by` الحالي. `CHECK` يجعل الثلاثة كلها non-null للغرض المباشر وnull معًا لأغراض planned/rebook. لا صف pending committed؛ صف provenance وسطر audit والموعد تُثبت أو تُراجع ذرة واحدة. `FK users(id) RESTRICT` يحفظ هوية الموقّع. الصف كله immutable. legacy بلا صف ولا backfill.
3. بصمة الـintent تُحسب من طلب الحجز **قبل** قراءة إعدادات أو defaults أو الخدمة المتغيرة، وبعد تنقية صارمة وحدود الحقول (patient/date/time؛ اختيار المدة الصريح أو auto؛ serviceId/type؛ doctor/chair؛ note؛ override؛ isNewPatient؛ purpose/bookingIntent). لا يدخل فيها السعر أو مدة/اسم خدمة قابلان للتغيير لاحقًا. actorUserId يُقارن مستقلًا. نفس UUID بجسد أو فاعل مختلف: `409` عامة بلا كشف بيانات الحجز الأصلي.
4. ترتيب POST **والاستعلام** واحد: signed/basic parse خارج المعاملة → تسلسل advisory مخصص لـUUID أولًا داخلها → reset fence المشترك → fresh user/session/permissions/scope بعد الانتظار → day/business locks إن كانت محاولة إنشاء. لا يُمسك قفل user قبل UUID. تسرية UUID تحصل قبل judgment السعة/الخدمة حتى لا يسبق replay رفضٌ بسبب حالة تغيّرت بعد نجاح أول محاولة. التفرد DB هو الحكم الأخير عند سباق/تصادم hash. لا تستمد سلطة من session قديم أو من GET فقط.

   `POST` يبقي `requireSession` القائم خارج المعاملة كفحص رفض تمهيدي قد يهيّئ schema وفق مسار الهجرة المرقّم، ولا يُبنى عليه قرار الصلاحية النهائي أو لقطة خدمة. أما `GET` الاستعادة فيقرأ توقيع الجلسة فقط خارج المعاملة، ولا يهيّئ schema إطلاقًا؛ يتحقق من الحساب والصلاحية داخل معاملة القراءة، ويردّ `503` عند غياب سجل 0095.
5. قبل الحجز، وبعد fresh auth، يفحص الخادم وجود UUID. يقارن `actor_user_id` و`recorded_by` **كلًّا مستقلًا** مع هوية المستخدم الحالية، ثم fingerprint وسلطة الوصول الحالي للمريض. إن تطابق الكل، يعيد `appointmentId` و**الحالة الحالية** مع `replayed=true` من الصف المحفوظ، بلا INSERT أو إعادة audit/رسالة. لا يعيد snapshot الحالة القديمة ولا يفتح مريضًا غير مصرّح. إذا كان UUID غير موجود، يُستكمل الحكم والكتابة المعتادة بنفس المعاملة. اختلاف actor/username/hash رد `409` عام.
6. مسار الاستعلام عن النتيجة بالـUUID يأخذ قفل التسلسل **قبل** fresh auth الداخلي، وبنفس ترتيب POST؛ إذا كانت المحاولة الأولى ما تزال جارية ينتظرها، ثم يعيد committed ID/status أو `not_found`. `not_found` ليس إذنًا لمفتاح جديد؛ يمكن إعادة **نفس** POST بنفس UUID فقط بعد تأكيد نتيجة الاستعلام، مع تمييز `session_expired/denied` عن نتيجة غير معروفة. إن تعذّر الاستعلام أيضًا، يبقى UI في «النتيجة غير مؤكدة» ولا يفتح نقرة حجز جديدة تلقائيًا.
7. planned-visit scheduling/rebook له ارتباط تشغيلي/expected old ID منفصل؛ الصف البديل يأخذ provenance تاريخيًا جديدًا ولا ينسخ UUID المباشر. إلغاء حجز ناجح لا يمحو receipt؛ replay يعيد ID والحالة cancelled، وإن أراد المستخدم حجزًا جديدًا فهذا فعل جديد بمفتاح جديد بعد رؤية حالة القديم.

## اختبارات حمراء قبل عرض UI

- lost HTTP response بعد COMMIT ثم `GET commandId` / إعادة POST بنفس المفتاح يرجع ID واحدًا؛ `appointments` وprovenance وaudit لا تتضاعف. بعد ROLLBACK يُسمح بإعادة نفس المفتاح فقط.
- طلبان متزامنان بنفس UUID أو بتاريخين مختلفين لا يحفظان إلا أمرًا واحدًا، و`pg_blocking_pids` يثبت ترتيب lock بلا دورة مع reset/day. UUID آخر يبقى أمرًا مستقلًا.
- تبديل actor، الجسد، أو سحب صلاحية/تغيير patient scope أثناء الانتظار يرفض بلا تسريب، مع عدم إعادة عرض بيانات لموظف فقد صلاحية الخطط.
- تحديث الخدمة/المدة الافتراضية بعد COMMIT لا يغيّر replay، لكنه يُعاد تحكيمه عند محاولة لم تحفظ. لا استنتاج plan/category من service text.
- full SQL + full archive restore يحفظ UUID/hash/actor والـunique/immutable guards؛ لا تدوير مفتاح ولا صف مفقود بعد restore.
- legacy بلا purpose يبقى مستجيبًا بالشكل القديم، ولا تُكتب له provenance ولا يُطلب UUID. planned/rebook يحفظان مصدر الخطة القديم مع UUID null.

**بوابات الإطلاق:** schema source/checksum/validator مجمّدة ومراجَعة، اختبارات PG18 وHTTP hosted خضراء، وUI يصرّح بـ«النتيجة غير مؤكدة» بلا وعد بحفظ غير مثبت. مسار الاستعادة `GET commands/[id]` توقيع فقط قبل معاملة قراءة تتحقق من الحساب والصلاحية؛ لا `ensureSchema` فيه، وغياب 0095 يردّ `503` مغلقًا. لا DDL حي ولا تعديل PR #514.

**أثر الحذف:** FK `actor_user_id → users(id) RESTRICT` يحفظ صاحب القرار ويمنع حذف حساب له حجز مباشر مصنّف. يجب فحص `deleteUser` وإظهار رفض واضح قبل أي حذف، لا الاعتماد على SQL 500 ولا إزالة الـFK لتمريره. هذا أثر source لم يُنفّذ بعد.
