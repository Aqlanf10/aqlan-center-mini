# Aqlan Center existing reporting audit

## Conclusion

The center already has extensive reporting: 35 unified report types, 21 printable document families, and separate financial, accounting, inventory, laboratory and administrative views. The next work should make those existing outputs agree on their data, dates, permissions and currency meaning. It should not create another financial engine or a second competing reporting backlog.

The highest-priority source findings concern collections amounts and filtered totals; doctor access to recall contacts and inventory cost; saved consent integrity; supplier balances; and historical/date-window consistency. Several reports also truncate operational evidence or export only part of what is visible. Each finding below has a bounded acceptance criterion. A source finding does not establish that a real patient record was affected.

## Organizing the existing reports

Use the existing report center as the index, with clear links to the authoritative module screens rather than duplicate calculations. A useful reading order is:

1. Daily operations: arrivals, appointments, recall, chair/provider flow and capacity.
2. Patient and clinical work: patient/dossier, treatment plans, specialty activity, prescriptions, referrals and consent.
3. Money and accounts: invoices, receipts, collections, patient debt, shifts, expenses, accounting and doctor commissions.
4. Laboratory and materials: order status, laboratory accounts, suppliers/payables, inventory movement and value.
5. Control evidence: reconciliation, exceptional historical records, audit logs, settings history, export and backup/readiness evidence.

For each report, its heading or help text should state purpose, allowed audience, authoritative source, event date, row grain, native/settlement/base-equivalent monetary basis, effective filters, result limits, reversal handling, historical/current basis, and output coverage. These are contracts of existing reports, not new feature requests. Start with incorrect financial amounts and exposed fields; improve navigation after correctness.

- The older daily report has its own bounded correction work. Its known first-invoice allocation, duplicated debt, missing cross-currency payment-only row and unsatisfied-filter observations are recorded as that work's context.

- Source-verified security and financial defects are prospective corrections. They do not authorize bulk historical rewrites, credential changes, record deletion or backup deletion.

Read caps must not masquerade as full totals. Corrected source must receive its own focused and full CI, review and exact deployment verification before its roadmap state advances to released.

## Source verified bounded gaps

### RPT COLLECTION MONEY P1

Native SAR/USD amounts are displayed 100 times larger in collections: `lib/reports.ts:2908` builds amountText from amountMinor; line 2927 passes summed native minor integers as KPI count. `components/reports/shared.tsx:69-74` renders counts with toLocaleString, while `lib/money.ts:48-52,122-128` specifies a divisor of 100 for SAR/USD. A synthetic source example is 1250 minor representing 12.50 SAR but displayed as 1250 SAR. The stored money itself is not changed. `debtMode=collected` uses the same path.

Acceptance: canonical currency formatting in row, KPI, CSV/Excel and print for YER/SAR/USD, 12.50 SAR/12.50 USD, negative refund movement, zero and large safe integers; preserve raw minor values for calculations. Native tender, settlement currency and recorded YER equivalent must have distinct truthful labels.

### RPT COLLECTION FILTERS P1

`reports.ts:2885-2889` classifies all period payments into old/new settlement KPIs before `2893-2896` applies tender currency, method and receiver filters to rows. Thus filtered detail and headline totals describe different populations. `filtersLabelOf:1229-1242` still prints those filters.

Acceptance: every displayed collection amount clearly states population and currency basis; selected tender/method/receiver rows reconcile to corresponding native and settlement totals, including cross-currency receipts and reversals. Do not re-run FIFO on a filtered payment subset and mislabel the result historical old-debt allocation. Either preserve full chronological allocation then select attributable events, or omit/qualify old-new breakdown for unsupported scoped views. Include same-day ordering, multiple receivers/methods, opening debt, prior credit and refund fixtures. Existing daily report logic remains outside this slice.

### RPT PERIOD EXPENSE COMPARISON P1

`loadContext` loads expenses only within current filters.from/to (`reports.ts:1058-1062`). `monthlyReport` calls `periodSummary` for the earlier comparison range (`1679-1707`), but periodSummary sums from that already-current-only array (`1627`). A disjoint prior period necessarily shows zero expenses even when source rows exist. This is a report data-range defect, not a new expense writer.

Acceptance: load the union of current/comparison expense ranges, or separately aggregate both under the same canonical expense semantics. Prior-month/year expenses and reversals remain visible; zero is only returned when the period truly has none. Compare boundary dates and empty current period with nonempty prior period.

### RPT DEBT DETAIL CUTOFF P1

Outstanding debt rows are titled as of filters.to, and balanceMinor uses that cutoff. However `reports.ts:2025-2032` sums billedMinor/paidMinor without a cutoff. Later transactions change components of an earlier report while its balance stays cutoff-scoped. Picked plan metadata/current plan-paid values also need explicit current labels; these are not the authority for debt.

Acceptance: invoice/payment/opening components shown as-of obey the same cutoff and currency as balance; a later invoice or receipt does not change earlier components. Current agreement context must be separately labeled or omitted. Preserve PR208 patient-statement behavior. Do not claim immutable historical reconstruction from mutable current invoice/opening state.

### RPT MONTH WINDOW AND SNAPSHOT TOTALS P1

Annual and debt-movement loops construct full month boundaries from from-year only (`reports.ts:1756-1762,2118-2126`). Custom midmonth periods include outside-period invoice/payment rows; cross-year ranges omit subsequent years. Debt-movement headline opening/closing uses exact range but monthly flows use expanded months. Annual outstanding and debt-movement opening/closing columns do not set aggregate:none (`1853-1863,2191-2197`), so shared table footers sum snapshots (`shared.tsx:41-51,308`). That sum is not an end balance.

Acceptance: clip each month to requested interval, iterate across year boundaries, and retain exact period labels. Boundary transactions on either side are excluded. Snapshot columns are nonadditive; period-opening/closing is presented explicitly once. Expense-only months remain represented, even with no billable/visit activity. Test partial months, leap February and December-to-January.

### RPT FINANCE CATEGORY VISIBILITY P1

The financial-summary API aggregates arbitrary category strings (`db.ts:13423-13437`), but the page renders only built-in EXPENSE_CATEGORIES whose net value is positive (`app/finance/reports/page.tsx:218-231`). Existing custom categories and negative reversal-only categories therefore contribute to total expense but disappear from its breakdown. Voucher category text also reads the static map (`app/print/voucher/[id]/page.tsx:59-63`), so custom labels can be blank.

Acceptance: render every actual category key, preserve signed values, resolve current catalogue labels with explicit code fallback, and reconcile the category breakdown to its summary. Cover custom, renamed/inactive, missing-catalogue, zero-net and negative categories. Preserve expense-permission projection and do not invent classifications. This extends the already-confirmed expense observation; deduplicate with the clinic-close expense work.

### RPT SERVICE MEASURE CONSISTENCY P2

Finance summary's top services uses COUNT(*) and SUM(invoice_items.total_minor) (`db.ts:13384-13390`) and labels output income with “service × count”. Unified services uses summed quantity and allocated post-discount net (`reports.ts:2971-2997`). A quantity-three discounted invoice yields inconsistent counts/values between existing reports.

Acceptance: one stated measure per surface; reuse canonical net allocation if called net income/value and quantity if called service count. If gross billed line value is retained, label it explicitly and distinguish row count from quantity. Test quantity-three, repeated description, discount, cancelled invoice and same service in multiple currencies.

### RPT FILTER CONTRACT P2

The common FilterBar exposes doctor, specialty, service, currency, patient/debt status, method and receiver for all reports (`shared.tsx:646-763`); the generic filter label repeats selected values without proof each engine applies them. Services lacks currency filtering in its line loop; monthly/annual money loops ignore currency/method/receiver; other scoped module instances are enumerated separately. Existing applied-request identity protection does not fix unapplied engine semantics.

Acceptance: a per-report allowlist declares supported filters and their population/basis. Unsupported filters are hidden/disabled or rejected/explicitly ignored without an applied-filter claim; every supported filter has contrasting fixtures. Avoid one broad rewrite: prioritize money reports, then operational ones. Preserve existing URLs/saved views with visible migration guidance where necessary.

### RPT EXPORT COVERAGE P2

`ReportView.tsx:162-182` exports only safeColumns/applied.rows; its monthly/sections rendered at 210-247 are not passed to export. Annual and debt movement have only monthly, so no CSV/Excel button. `report-export.ts` emits headers and rows only, omitting title, resolved period, generation metadata, notes and cap warnings. It protects CSV formula content and XML text cells; keep these defenses.

Acceptance: label current export “main table” immediately, then add bounded full-report export including monthly/sections with their schemas, currency semantics, exact applied period, source basis and cap indicators. Screen/print/export totals reconcile. No snapshot field should be summed by default. Report-specific evidence packets must not silently lose audit sections.

### RPT PRINT CLINIC CLOCK P2

Invoice/current statement prints slice UTC ISO dates, while receipt/voucher print uses server-local Date getters. Shift Z-print explicitly uses CLINIC_TIME_ZONE (`app/print/shift/[id]/page.tsx:21-28`). Consequently the same recorded transaction can receive a different paper date near clinic midnight if the server zone differs. This is source-confirmed inconsistent clock selection, not an observed wrong Production receipt.

Acceptance: reuse explicit clinic-time formatter for document timestamps; preserve date-only clinical/planning fields without shifting them. Cover an instant on opposite UTC/clinic calendar dates and assert matching receipt/invoice/statement/day-report date.

### RPT HISTORICAL BASIS P2

`loadMovements` selects currently noncancelled invoices and current openings (`reports.ts:324-347`); balancesByCurrencyAt only filters those surviving rows by date (`790-802`). A historical cutoff is therefore a current-derived projection, not immutable closing evidence. Existing PATIENT-REPORTS and accounting carry-forward releases remain valid within their bounded contracts.

Acceptance: present current-derived basis and generated time consistently in screen/print/export; retain later-event uncertainty. Any true historical event reconstruction is a separately designed slice requiring trustworthy cancellation/opening histories. No history rewrite or Production correction is authorized by this report audit.

# Clinical reception and patient reporting contracts

## Shared contracts used by the rows

**Authority.** `A` = admin; `R` = reception; `F` = accountant. Unified reports use the same `canAccessUnifiedReport` at API and official print. In this scope only `specialty` is available to F; A can read all. Doctors, assistants and cashiers cannot access these unified IDs. A doctor may instead access patient-scoped clinical records/prints under `canAccessPatient`. Its normal rule: A/R allowed, doctor requires current active account plus own-patient relationship or explicit all-patient permission; a requested extra permission must also be true. Assistant is limited to today's patients with no extra doctor permission, and outer route allowlist further restricts reachable paths.

Sources: [report access](https://github.com/Aqlanf10/aqlan-center-mini/blob/f20ea16eebce438cb7e46b3e68b601a3f627496b/lib/report-access.ts), [API](https://github.com/Aqlanf10/aqlan-center-mini/blob/f20ea16eebce438cb7e46b3e68b601a3f627496b/app/api/reports/route.ts), [official print](https://github.com/Aqlanf10/aqlan-center-mini/blob/f20ea16eebce438cb7e46b3e68b601a3f627496b/app/print/report/page.tsx), [patient access](https://github.com/Aqlanf10/aqlan-center-mini/blob/f20ea16eebce438cb7e46b3e68b601a3f627496b/lib/patient-access.ts), [outer role gate](https://github.com/Aqlanf10/aqlan-center-mini/blob/f20ea16eebce438cb7e46b3e68b601a3f627496b/lib/role-routes.ts).

**Clock.** `clinic` means configured `CLINIC_TIME_ZONE`, default `Asia/Aden`; movement timestamp SQL uses `AT TIME ZONE` and stored business dates remain dates. Relative report period resolves using DB clinic today. An arrival-date cohort with current state is not an immutable historical snapshot.

**Output U.** `/reports` screen + `/api/reports?report=ID` JSON + `/print/report?report=ID` official print + client CSV/Excel of the main table after selected columns/sort. ### M02 — Unified supplier balances bypass effective obligation and legacy settlement semantics (high-priority financial truth)
