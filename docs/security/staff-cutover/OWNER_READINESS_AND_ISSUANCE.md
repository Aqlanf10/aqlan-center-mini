Design-only baseline: `2b0de02` (2026-10-27). Read with `CONTRACT.md` and `CANONICAL_READ_SNAPSHOTS.md` (the companion read-snapshot design). This artifact authorizes no installation, public route, issuer enablement, grant, owner binding, credential operation or Production action. No secrets, live data, or backups were accessed. Synthetic acceptance proves code behavior, never the identity or authority of a real owner.

## 1. What the current source establishes (and does not)

* `lib/staff-identity-substrate.mjs` initializes **quarantined** storage, appends target generations and subject/binding history under an exclusive lifecycle advisory fence and generation/revision CAS. Its `assertStaffIdentitySourceRestoreAllowed` always refuses. Its numeric user existence check is not proof of human ownership or continuity after restore.
* `__tests__/fixtures/staff-identity/frozen-0076.sql`, reflected in `lib/staff-identity-substrate-catalogue.mjs`, models control states `unbound`, `prepared`, `quarantined`, `prepared-recovery`, `active`. It generates a target realm, protects owner rows, increments control/account/provider epochs and prevents active→legacy downgrade. Prepared control requires an active admin row plus conversion digest/recovery reference. Those fields and role checks are **structural constraints, not trusted provenance**. A caller-supplied digest/reference or SQL update cannot establish ownership. This is frozen fixture/proposal evidence, not proof of installed Production control or an available trusted preparation service.
* `lib/staff-runtime-schema.mjs` proposes v2 readiness: exact active control epoch and owner subject, complete canonical account bindings, unchanged history at seal. It rejects **every** update from ready. Consequently ready→quarantined, post-ready generation changes and owner recovery are not implemented lifecycle operations; do not evade the guard with trigger disablement or direct SQL.
* `lib/staff-operation-runtime.ts:load` checks schema, history, ready/control anchors, sorted user/binding locks, current account credential/permission/provider tuple and exact capability. Six actions exist. `staff.permissions.edit` is admission, not an editor implementation. `ownerContextFromTrustedBinding` validates shape; the trusted caller must establish its provenance.
* `lib/staff-durable-session.ts` verifies exact signed claim shape through a private handle and rechecks expiry. This is **not** current DB admission. `lib/auth.ts:createSessionToken` explicitly rejects canonical markers; there is no supported durable issuer. The credential version is an HMAC of the stored password hash, not a password or proof of human ownership.
* `app/api/auth/login/route.ts` still uses legacy lookup/token creation. It preserves bounded JSON/form parsing; two rate-limit layers; generic bad-credential responses and dummy password work for absent users; account-only counter clearing after success; trusted redirect construction; HttpOnly/Lax/Secure cookie handling; no token in browser JSON. `consumeStaffLoginAttempt`, `consumeLoginAttempt`, and `clearAccountLoginAttempts` in `lib/db.ts` call `ensureSchema`. Canonical entry therefore needs reviewed non-initializing counter storage access, not blind reuse across a marker-bearing boundary. This is a prerequisite, not a reason to remove either limit.

## 2. Trust root and required decision, before any live preparation

No application role, username, numeric ID, successful legacy session, setup endpoint, imported password, source registry, or synthetic ready row appoints an owner. Password authentication proves possession of the selected account credential, **not** the right to become clinic owner.

Proposed live trust root: a separately authenticated, target-operating administrative control process, with an explicit action-specific approval from the authorized clinic owner/operator obtained outside the untrusted application account being appointed. The process must bind the approval to the precise target deployment/database identity, target realm, current generation/revision/control epoch, and independently verified intended owner/account incarnation. Approval cannot be accepted from request JSON or a preexisting staff token alone. An authenticated chat approval is evidence only if the operator identity and authority to approve that target were actually established; this document does not assert they are established.

**Unresolved policy/implementation gate:** who can approve and execute, how their identity and clinic authority are independently verified, where tamper-resistant approval/audit evidence lives, and whether two-person confirmation is required. Options are a reviewed organization change-control identity or a reviewed attended operator ceremony with independent owner verification. Neither is implemented or silently chosen here. If no trusted provenance exists, stay quarantined. Do not invent a bootstrap credential, new signing secret, magic recovery token, or public ready toggle.

An approval record needs: unique operation ID, purpose (`initial-binding`, `recovery`, or separately reviewed replacement), target identity and anchor tuple, intended **target-local subject/incarnation** plus human verification reference, complete conversion-plan digest, permitted changes, expiry, authenticated approver/executor evidence, and expected prior state. Retain references/digests and nonsecret outcomes, never plaintext passwords, hashes, session tokens or signing material in audit. Digest integrity alone is insufficient without authenticated provenance.

Target-local subjects must be newly allocated through reviewed quarantine binding. A source user row ID is only a locator. When restored/recreated data occupies the same ID, it must not inherit a surviving `staff_identity_current` association: a reviewed target mapping must explicitly retire the old incarnation and bind a new subject, append events, and invalidate old claims. Unknown continuity denies. No bulk deletion/rewrite of registry history and no source authority import.

## 3. Proposed quarantine→ready protocol

These are future transaction-owning administrative commands, not installable SQL in this artifact. Separate control-state activation from identity readiness; `control.active` alone never permits issuance.

1. **Plan without authority.** Inspect exact reviewed schema and target anchors read-only. Produce explicit account-by-account canonical permission/provider mapping and target subject continuity decisions, including inactive accounts. Current ready constraint requires every account be canonical and bound. Do not derive broad grants from legacy roles. Bind approval to plan digest and exact expected anchors; changed accounts require a new plan/approval, not silent refresh.
2. **Prepare under exclusive lifecycle fence.** Revalidate approval authenticity, scope and expiry; lock control→state→sorted accounts→sorted current bindings→providers. Prove history and all expected epochs/subjects. CAS includes control state/epoch, realm, generation, registry revision, owner subject and affected account/permission/provider revisions; a mismatch aborts. Prepared control retains a provenance reference and digest but no usable sessions. Stage identity mappings only through append-only quarantine events, with a complete auditable plan. Preparation may be committed as a resumable checkpoint only if it remains nonauthorizing.
3. **Seal in one transaction.** Reacquire exclusive fence and all fresh proofs. Validate complete plan, owner human-provenance reference, current exact target owner subject, active eligible owner account, canonical permission documents and current provider links. Perform approved conversion/control activation and ready seal, with audit and idempotency outcome atomically. If separated into multiple reviewed transactions, every intermediate state must still fail issuer admission, and final seal must validate the complete committed history again. The ready seal changes no realm/generation/subject history; it pins its current control epoch/owner subject. Fresh readiness is not inferred from presence of v2 DDL.
4. **Commit result only.** Never acknowledge ready or release an issuance candidate before successful commit. An operation ID replay can return only a previously committed outcome for the identical authenticated request digest and target; a replay does not waive fresh current readiness checks or authorize another operation. Unknown commit outcome requires a read-only outcome lookup, not blind repeated activation.

Realm is immutable target provenance. Generation IDs, subjects and events are append-only; state/current pointers may advance only with reviewed transition rules and CAS. Registry revision cannot be reset or reused. Ready-state lifecycle needs a separately reviewed schema/probe/catalogue revision because v2 currently rejects mutation from ready. A future suspension/recovery event must preserve history, invalidate the prior generation/control seal and disable issuance before work resumes. The exact new transition schema is an open design gate, not permission to change the current guard.

## 4. Common locking and revocation semantics

Coordinate with the canonical read-snapshot proposal:

`lifecycle fence → control → identity state/history → users sorted by ID → current bindings sorted by user ID → providers sorted by ID → permission validation → domain reset fence → operation key → domain rows`.

The existing fence is `aqlan.canonical.identity.substrate.v1:${schema}`. Issuance and ordinary canonical mutations acquire it shared transactionally before authority rows. The proposed read-only RR reader acquires it session-shared **before** BEGIN/snapshot creation. **Every authority-changing writer must acquire it exclusively before row locks**, including password/username/account state, permissions, provider/link/epoch, control, binding and generation changes. No shared→exclusive upgrade: the capability editor needs a dedicated transaction-owning authority writer that acquires exclusive first and then admits its actor. Calling existing `withStaffOperation` and upgrading in its callback can deadlock and is not this protocol.

This is an extension to the current writer contract, not established coverage. Enumerate all writers, maintenance tools, restore/setup paths and trigger interactions; prevent bypass by app DB privileges/approved entrypoints and independently test it. A row trigger that waits for this fence after acquiring a row lock is too late and risks inverted ordering. Superuser/unaudited SQL is outside any application proof; do not claim the fence protects against arbitrary database administration. Installation/schema lifecycle also requires the legacy maintenance drain and its lifecycle fence in a separately checked total order; do not compose unknown lock hierarchies by guesswork.

A revocation request can wait behind an already admitted bounded read/operation. Revocation **linearizes at committed exclusive mutation**, not at the instant an operator clicks. New admission after that commit must deny stale claims. A snapshot final reread is not fresh visibility of a concurrently committed change; the common fence prevents that concurrent commit. Bound transaction/read duration, lock wait and request cancellation, and destroy a connection if session-fence cleanup cannot be proven. Expiry is wall-clock checked after waits and immediately before protected work/result release; do not rely on transaction `now()`. No guarantee can revoke bytes already delivered or prevent a response reaching a client after expiry. Immediate cancellation/streaming semantics would need another reviewed protocol. Domain ownership reassignment also needs an explicit choice: if it revokes record eligibility immediately, its writers join this exclusive-fence protocol; otherwise the reviewed reader contract must explicitly permit snapshot-time record scope. Do not silently treat a patient/provider reassignment as harmless domain data.

## 5. Password-authenticated durable issuance

A private server-only transaction-owning issuer accepts bounded login input, **not caller claims, roles, or a userId asserted as authority**. Its public route remains disabled pending review.

1. Apply existing body/origin/proxy/redirect rules and both persistent limiter layers before expensive password verification. Preserve key normalization, shared multi-instance enforcement, source-counter behavior, 429/Retry-After and generic credential failure semantics. Replace `ensureSchema`-coupled access only with reviewed preinstalled-storage primitives. Database/limit failures fail closed; no in-memory bypass.
2. Read a minimal candidate using explicit canonical, non-initializing lookup. Return no hash/private identity externally. Perform existing `verifyPassword` semantics; preserve absent-user dummy work and bounded concurrency. Do not auto-rehash, reset, migrate passwords or alter credentials as part of issuance. Expensive verification can occur outside the final lock, but capture the exact candidate account/subject/hash/epochs internally.
3. Start READ COMMITTED transaction, acquire shared lifecycle then ordered authority locks. Reprobe exact runtime schema and validate active control, ready seal, full target history, owner binding and user current binding, current username/active/canonical mode, permission document policy/revision, credential version/account epoch, and exact active doctor/provider epoch when linked (null must match null). Compare the captured candidate incarnation/hash and epoch to the current row; if anything changed, fail/restart a new bounded login attempt, never use old password proof with new authority. A malformed document/provider denies issuance even if password matches. This is entry authentication, not an invented `staff.view` requirement for all users; each later operation needs its own exact capability.
4. Derive all `DurableSessionClaims` fields from the proved locked tuple, including current username and `expiresAt` using existing `SESSION_DURATION_MS`. No legacy role field or permissive projection is minted. A future private signer must be distinct from forbidden `createSessionToken`, reuse the reviewed signing configuration without exposing it, produce exactly the existing strict durable shape, and remain inaccessible to arbitrary claim callers. No secret is read/created/configured by this design work. Full signer/key-domain separation changes are a separate review decision, not a hidden new credential deployment.
5. Revalidate wall-clock expiry, authority and transaction ownership immediately before commit; stage the signed token privately and record nonsecret success audit atomically. On rollback/signing/commit failure discard it. Only after confirmed commit emit HttpOnly/Lax cookie with current Secure rules, bounded lifetime and no-store response. Never return token in browser JSON. Clear only successful account counters (not source limits), preserving existing best-effort cleanup semantics after committed success; cleanup failure cannot create another token or weaken future limits.

A revocation may commit after issuer commit but before cookie delivery. The resulting stale cookie must fail on its **first live admission**; issuance is not an entitlement to future actions. Authentication/me and the shell use the same current canonical admission/projection, never a durable verifier alone. The selected canonical cookie cannot fall through to a legacy Bearer on any failure. Missing/ambiguous/malformed envelopes deny according to one reviewed selection rule. Legacy mode is only a distinct marker-free deployment/fixture, never a per-request fallback in canonical state.

## 6. Expiry, logout and recovery limits

Account epoch/credential version changes revoke the user's existing durable claims; permission revision and provider/clinical epoch changes deny stale grants; realm/generation/control/subject changes deny old authority. Current exact registryRevision matching means a binding event invalidates **all** sessions carrying the prior registry revision: document this operational cost, do not silently weaken matching. Current ready guards mean post-ready binding/generation lifecycle is unavailable until explicitly designed.

Cookie-clearing logout is browser-local, not server-side revocation of a copied token. No session ID/revocation table exists in durable claims. Minimum first-slice contract: disclose this behavior; account-wide revocation through a separately authorized epoch mutation can invalidate all copies. If per-session logout/revocation is required, approve a session-record/schema/claim protocol before claiming it works. No token refresh/sliding-expiry bypass is included.

Malformed/partial schema, missing provenance, stale CAS, expired approval, history mismatch, audit failure, unavailable DB, and ambiguous commit all deny without legacy fallback. Recover by diagnosis and a fresh narrowly approved command, not by disabling triggers. Prepared-but-unsealed work remains quarantined and nonauthorizing. A crashed prepared operation can resume only with original committed outcome/digest, current anchors, unexpired applicable approval or renewed approval, and complete validation; otherwise leave it blocked. Replacing a lost owner credential is a sensitive distinct operation and is deferred, not bundled into recovery.

**Rollback is not “deploy old code.”** Old code can ignore new guards/markers and recognize old role-shaped tokens; DB triggers cannot stop unauthorized reads by old binaries. Remove/drain old processes and verify only compatible binaries can access the target before canonical markers/activation. On trouble keep traffic stopped or deploy a reviewed guard-aware forward fix. Do not remove canonical tables/markers, downgrade authorization modes, rewrite immutable history, restore source control, or automatically reopen legacy auth. An approved target recovery must retain target authority provenance and rebind restored account incarnations explicitly; source restore cannot carry target authority. No Production backup export or restore is needed or authorized for this design.

Use an isolated real PostgreSQL fixture and built HTTP application, not library-only callback success. Fixture owner provenance must be explicitly labeled synthetic and have no live preparation capability. No generic role-based adapter, new inventory features, AI/Dot expansion, setup shortcut, restore route or activation flag.

Acceptance must include:

* Real password→signed cookie→auth/me→shell→directory→owner edits allowed permissions→narrow user's stale token denied→fresh login reflects exact allowed scope. Direct API attempts still deny hidden UI actions. Marker-free baseline login/shell remains separately passing.
* Wrong password/missing user/inactive account, malformed canonical document/provider, unknown owner provenance, partial/v1/quarantined schema, control/ready mismatch, forged/copied handles, mixed envelope downgrade, stale subject and ID reuse; none issue a usable token or invoke legacy lookup.
* Two prepares/seals against the same CAS, changed conversion plans, approval expiry during lock wait, duplicate operation IDs with different digests, audit failure and unknown commit: exactly one valid committed outcome or fail closed. Test proposed lifecycle using synthetic evidence only.
* Password/provider/permission/account revocation racing with password verification and final issuance; issuer blocked behind revoke; revoke blocked behind admitted reader; expiry after waits; stale cookie delivered after revoke; sorted actor/target editor locks; no shared→exclusive upgrade; permission write/audit rollback together on final failure.
* Failed signer/commit never sets a cookie; no plaintext password/hash/session token in logs or responses; both limit layers survive concurrent instances, account cleanup never clears source counts, schema bootstrap is never reached by canonical request.
* Session-level reader fence releases on every failure, cancellation and pool-reuse path; authoritative SQL writers all obey the exclusive-first protocol. Existing fixture direct writes are not evidence of production writer coverage.

**Live gates are separate, per action:** approve target owner-provenance procedure; separately approve any real owner binding/access conversion, installation, issuer activation, credential change or recovery. Passing tests supplies no such approval. This artifact carries no actual approval record. Before activation the whole existing clinic—not merely this administrative slice—must pass marker-bearing canonical built-application journeys for all required routes/semantic branches, public/portal separation and operational effects. Readiness remains **NOT_READY**. The owner chose a drained maintenance cutover on a clinic holiday (date to be scheduled); neither concurrent legacy/canonical authority nor a feature flag replaces that window.
