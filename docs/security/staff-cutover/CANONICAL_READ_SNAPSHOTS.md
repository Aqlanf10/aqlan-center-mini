## Current behavior, not proposed guarantees

* `lib/staff-operation-runtime.ts` owns READ COMMITTED, assigns an XID, takes a shared transaction lifecycle fence, validates canonical authority using `FOR SHARE`, binds private exact-action handles to client/XID, and freshly revalidates before commit. It currently admits six actions. It is **not a READ ONLY snapshot runtime**. Do not introduce a caller-controlled `skipLocks`, isolation, or read-only flag.
* `lib/legacy-staff-readonly-snapshot.ts` and `lib/hr-identity-read.ts` already acquire a shared **session** lifecycle fence before BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY, then authenticate/read in one snapshot, check expiry, commit/rollback and explicitly unlock/discard. They remain legacy-only; the former has a preflight→ensureSchema maintenance gap. The canonical proposal must have no ensureSchema/bootstrap path.
* `lib/financial-read-snapshot.ts` provides coherence, not admission; its shared-local-connection escape is not a canonical security boundary. `lib/backupReadOnly.ts` uses a short READ COMMITTED READ ONLY authentication transaction, not a full export lifetime. Its no-bootstrap promise must survive migration. `lib/staff-authority-snapshot.ts` is explicitly an observation adapter, not authentication.
* Existing lifecycle functions in `lib/staff-identity-substrate.mjs` take the exclusive fence before authority rows. They operate in quarantine; they do not establish a complete authority-writer revocation protocol today.

## PostgreSQL facts and design consequences

1. RR fixes visibility at its first query; acquiring a blocking advisory lock *inside* RR can pin a snapshot preceding the writer being waited on. Acquire the shared session fence before BEGIN, then start RR. A final SELECT in the same RR snapshot is **not fresh revocation visibility**. [PG18 transaction modes](https://www.postgresql.org/docs/18/sql-set-transaction.html), [application consistency](https://www.postgresql.org/docs/18/applevel-consistency.html).
2. READ ONLY is a high-level restriction, not a guarantee of zero disk writes; it does not make arbitrary SELECT functions harmless. Only reviewed domain SELECTs/functions are allowed; no temporary-table writes, DDL, sequence allocation, repairing helpers, side-effect functions or row-locking queries. [PG18 transaction modes](https://www.postgresql.org/docs/18/sql-set-transaction.html).
3. `pg_current_xact_id()` assigns a top-level XID if necessary; `_if_assigned()` may return NULL and cannot identify two otherwise read-only transactions. On PG18 primary, READ ONLY does not itself prevent XID assignment: the official source calls `GetTopFullTransactionId`, rejects recovery, and its assignment path has no READ ONLY prohibition. Thus “XID cannot work in READ ONLY” is incorrect, but “SELECT means no allocation” is also incorrect. XID allocation consumes cluster IDs/internal bookkeeping. Do not reuse the writer probe for this no-allocation reader. This is documentation/source analysis, **not a locally executed experiment**. [Functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-PG-SNAPSHOT), [official xid8 source](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/xid8funcs.c), [official transaction source](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/access/transam/xact.c).
4. Every transaction has a virtual transaction identity. `pg_locks` exposes the holding transaction and PID; the backend holds an exclusive virtual-XID lock. A narrowly selected self row is a proposed identity probe without XID allocation. `pg_locks` is not a globally atomic snapshot, so do not infer other transactions' authority from it. [Identifiers](https://www.postgresql.org/docs/18/transaction-id.html), [pg_locks](https://www.postgresql.org/docs/18/view-pg-locks.html).
5. Advisory locking is cooperative. Session locks survive rollback and are counted; session and transaction variants conflict on the same key. Explicit unlock or connection destruction is mandatory. [PG18 advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).

## Proposed owning protocol

Only a server-internal owning reader accepts an unforgeable `VerifiedDurableSession` from the selected signed envelope, an exact registered read action, and validated domain parameters. No arbitrary session JSON, legacy role adapter, client/pool override, caller-selected schema, isolation or SQL. Schema is trusted configuration. Reject unknown actions, partial/v1/quarantined authority, invalid tokens and expired tokens without legacy fallback.

1. Obtain an exclusively leased, clean connection to the authoritative primary (not a replica or transaction-pooling connection). Set bounded acquisition/query/transaction deadlines using a separately reviewed connection policy. Acquire exactly one shared **session** lock with `hashtextextended('aqlan.canonical.identity.substrate.v1:' || trustedSchema, 0)`. Any uncertainty about acquisition taints the connection. Revalidate signed-session expiry after this wait.
2. BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY. Inspect the exact canonical schema shape read-only; never repair it. Establish private transaction identity before handing control to domain readers. Proposed SELECT probe:

   ```sql
   SELECT virtualxid::text
   FROM pg_catalog.pg_locks
   WHERE pid = pg_catalog.pg_backend_pid()
     AND locktype = 'virtualxid' AND mode = 'ExclusiveLock' AND granted;
   ```

   Require exactly one nonempty identity; separately require `transaction_isolation = 'repeatable read'` and `transaction_read_only = 'on'`. Bind the identity to this leased client and a private, unique invocation object. This query shape and driver behavior must pass PG18 acceptance below before adoption; missing/ambiguous evidence fails closed, never falls back to NULL XID, PID alone, timestamps, or snapshot text.
3. In this same snapshot, validate all current authority invariants used by the writer runtime: active control realm/binding epoch; ready state, generation/registry revision and complete history integrity; protected ready-owner subject/control anchors and current active canonical owner; actor immutable subject/current binding, numeric account and exact username; active canonical account/account epoch and credential version; parsed permission document/revision; exact linked active doctor/provider incarnation and clinical epoch or required absence; exact action capability with trusted owner binding. No broad admin-role substitution. Revalidate session expiry after potentially slow admission queries.
4. Resolve record scope from that admitted capability set, not request fields or display projection. Every protected reader applies the exact operation's all/own/target/branch predicates in the same snapshot before selecting data. Provider scope uses the validated current linkage, not numeric ID alone. Multi-record/export queries must constrain every returned row and nested attachment/financial relation. Own-patient/appointment semantics require their own reviewed predicate, not a generic inferred rule. Unknown predicates deny. This design supplies a boundary, not new grants or invented HR/payroll/backup capability names.
5. Mint a server-private WeakMap-backed read handle bound to invocation, exact action, trusted schema, client, virtual identity, session and admitted scope/fingerprint. Domain modules receive narrow registered read methods, **not raw DbClient, pool, arbitrary SQL or transaction controls**. Each protected method asserts live handle/action/scope, checks actual virtual identity and modes, rechecks real-time expiry, and applies reviewed SQL. Serialize operations; do not allow detached concurrent queries or post-callback tasks. Frozen auth/me/capability/record projections carry no read or mutation authority; writers always require their independent exact-action admission.
6. Buffer a bounded plain-data result. After all reads finish, close the handle to further reads and await tracked in-flight work; require no outstanding work. Check transaction identity/modes, required scope validation and session expiry again. Optionally compare the same-snapshot authority fingerprint for implementation invariants, but never describe it as a fresh post-admission database read. COMMIT; require successful command completion, and recheck expiry before publishing the result. Revoke/delete private handle state on every path. Release the shared fence only after transaction completion. Return no data on failed commit, expiry, failed cleanup or uncertain connection state.
7. On failure, revoke the handle first, cancel/drain owned outstanding queries safely, ROLLBACK if transaction start was attempted, and explicitly unlock once if acquisition succeeded. Require exactly one `unlocked = true`; failed rollback/unlock, connection loss, uncertain acquisition, unexpected transaction boundary, changed identity or unexpected settings ⇒ destroy via `release(true)`, never recycle. Preserve the initiating failure and separately record sanitized cleanup failure. No secrets, SQL parameters or patient data in error logs. Before returning success, cleanup must be confirmed; an unlock failure cannot merely set a destroy flag and still publish data.

### Savepoints and escaped handles

The boundary owns BEGIN/COMMIT; it never accepts an already-running caller transaction, so it cannot commit or roll back a caller's transaction. It does not create, release or roll back a named “sentinel” savepoint to test identity: releasing an earlier savepoint can destroy later caller savepoints. A virtual-identity/mode SELECT does not alter savepoints. If a future trusted domain reader needs nested savepoints, expose a separately reviewed scoped API with unique private names; do not expand the initial surface. Top-level identity intentionally survives nested rollback; authorization must be established before any such savepoint. No raw query interface may escape. A stolen/copy-constructed/projected handle fails its private-map/owner binding; an escaped real handle is invalid once closing begins. Even valid identity checks cannot undo data a malicious trusted callback already exfiltrated: trusted server code and no SQL injection are explicit assumptions, not claims solved by TypeScript branding.

## Revocation, scope changes and writer lock order

**Chosen semantics: fence-linearized authorization, not immediate cancellation.** A read admitted under shared fence may finish before a concurrent revocation obtains exclusive ownership. Once a revocation commits and releases its exclusive fence, every subsequently admitted reader sees the changed authority and rejects stale claims. A pending request to revoke is not a completed revocation. A result may arrive over the network after revocation/expiry; previously disclosed data cannot be recalled.

This guarantee requires **all** authority-affecting writers to acquire the same exclusive lifecycle fence *before any authority/domain row lock*: credential/account activity and epochs, permission/revision, provider activity/clinical epoch/linkage, subjects/bindings, owner/control/readiness/generation/history and relevant schema lifecycle. Do not call current `withStaffOperation` (shared fence) and upgrade to exclusive: use a separately reviewed authority-command owner that starts exclusive, then validates actor and target. Trigger/admin/job/direct-SQL bypasses invalidate the guarantee. No adoption until the complete writer set and database-role restrictions are reviewed/tested.

Common order, aligned with owner/issuance design: lifecycle fence → control → identity state → sorted affected users → sorted current bindings → sorted provider rows → permission validation → domain reset fence → operation key → domain locks. Readers take no row locks. Ordinary domain writers retain shared lifecycle admission; any domain change that itself revokes record eligibility (for example ownership reassignment) must be classified: either it also takes exclusive lifecycle before rows, or the operation explicitly promises only snapshot-time record scope. Do not promise immediate ownership revocation while allowing uncoordinated domain reassignment.

Global exclusive authorization writers deliberately serialize behind bounded readers. Timeouts/cancellation, row/byte limits and short transactions are availability requirements; lock starvation/fairness or a maximum revoke latency is not guaranteed merely by this design. Large backup streaming, external uploads, cursors surviving return, multi-transaction pages, or effects outside the DB need a separate protocol. They are **not** silently covered by extending a snapshot forever. Existing backup functionality remains required by clinic cutover; this limitation is an unresolved migration gate, not permission to drop it.

## Required runtime acceptance and remaining gates (not established)

Run future integration tests only on a fresh owned synthetic PG18 cluster through the existing guarded runner/shared test lock; review any runner change first. Never inspect an unknown cluster or live database.

* Identity probe: RR READ ONLY self virtual identity is unique/stable across many SELECTs and nested SAVEPOINT/ROLLBACK TO/RELEASE; `_if_assigned()` remains NULL. Probe does not destroy later caller savepoints. End/restart transaction on same client changes identity; same/different-client escaped, forged, wrong-action/schema handles deny. Autocommit/default-RR cannot pass the owning lifecycle. Parallel/disconnected/aborted states fail closed. Separately demonstrate optional `pg_current_xact_id()` allocation works on owned primary READ ONLY, without making it the chosen implementation.
* Fence race: exclusive revoker commits while reader waits **before BEGIN**; reader then sees new epochs and rejects old token. Deliberately put lock acquisition inside RR in a negative control and reproduce stale visibility. Active reader blocks exclusive revoke until cleanup; after revoke completion a new read rejects. Exercise permission, password/account, provider and owner/binding changes, plus chosen scope-reassignment semantics.
* Enforce all authority tuples/history checks, exact capability and row predicates; deny unlinked/inactive/reincarnated provider, numeric-ID reuse, malformed permissions, quarantine/partial schema, invalid signatures and canonical→legacy downgrade. Verify no extra rows/columns or credentials in projections.
* Coherent invoice/receipt/allocation and HR temporal multi-query reads during ordinary concurrent writes; no mutation authority from their output. Marker-free legacy regression remains intact. No implicit ensureSchema/DDL/sequence/audit mutation or row locks in canonical read path.
* Expire while waiting for fence, during query, before commit and during cleanup; no returned result. Use wall time rather than transaction-stable `now()` for expiry; trusted clock policy must address clock skew/backward jumps. Verify abort, timeout, commit/rollback/unlock failures and dropped connection destroy/release behavior; subsequent pool borrower has no leaked session lock/transaction/handle.
* Test detached work, oversized result, denied SQL/control access, nested invocation, unauthorized direct HTTP access, and final serialization failure. Add actual built-application login→auth/me→shell→directory/edit/revoke journeys; library tests alone are insufficient.

Remaining gates: independent design review; prove complete authority-writer fence participation; approve bounded connection/deadline and clock policy; execute owned PG identity/lifetime/race tests; review exact first-slice record predicates and narrow query facade; separately design long backup/export and external effects. The original design-only change ran no tests. The bounded SQL-mechanics experiment below does not establish runtime correctness. No production cutover or whole-clinic availability claim follows.
