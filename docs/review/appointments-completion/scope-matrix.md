# Appointment request scope and remaining boundaries

This matrix describes this draft source change, not a deployed clinic or a percentage-complete claim. Final hosted CI must be read on the published head.

| Requested outcome | Implemented source and verification | Practical boundary |
| --- | --- | --- |
| Orthodontics, new orthodontic patient, endodontics, filling, prosthetics, awaiting prosthetics, other | `lib/appointment-category.ts`; quick booking, board editing and patient history; native persistence and browser category editing | Explicit appointment metadata; no backfill from notes, procedure names, diagnoses or treatment status. Existing records remain unclassified until selected. |
| One-click patient lists and searchable categories | Patient page buttons; API validation and existing scoped search/browse queries; 81 route tests and 2 native tests with 32 synthetic patients; settled-response mobile/desktop browser checks | Matches recorded appointment history, including earlier appointments, as labeled. It does not claim current clinical treatment status. |
| Patient, doctor, visit, plan and case linkage | Existing patient/doctor keys retained; planned/next-session doctor locked and preserved; same-patient stored clinical relations projected after transactional authorization | No inferred latest plan/case, label matching or name-based relationship creation. Destination authorization still applies. |
| Doctor duty by day, morning/evening/both, configured center hours and approved leave | Existing HR mappings/schedules and editable shift presets; shared transaction admission with settings/roster/leave/block locks; native contention and hours/buffer tests | Missing or ambiguous HR authority refuses booking. Unsupported partial-day leave data cannot establish available intervals and fails closed. Target mappings and schedules require separate Staging acceptance. |
| Staff confirmation, patient confirmation, lateness and attendance | Independent flags/filters; snapshot-checked staff confirmation, reset on movement; clinic-local lateness display; existing arrival/no-show paths retained | Staff confirmation is an employee report of patient confirmation. It neither asserts delivery nor marks arrival. Lateness alone never rewrites attendance. |
| Follow-ups, referrals and patient history | Protected follow-up service selection preserved; planned replacement keeps category; explicit roster fixtures for existing referral/rebooking tests | Broader orthodontic work and prescription branches are separate; no arbitrary composition was performed. |
| Lost responses, duplicate retries and account changes | Immutable UUID receipt, exact-body recovery, fresh account binding and fail-closed storage; native same-key concurrency and actual browser reload/retry journeys | Older inline patient creation lacks a durable creation receipt. An unknown creation outcome blocks another creation and directs staff to search; no duplicate-safe patient-create claim is made. |
| Reminder hour discrepancy | Browser checks of stored 09:30/15:30 times in Asia/Aden and America/New_York; clinic-midnight default-date test | A one-hour offset was not reproduced. The confirmed default-date issue uses clinic time; no unsupported claim of fixing an unobserved reminder defect. |
| Reuse prior work without conflicts | Exact PR514/515 ancestry checked; prior515 type and generated-schema fixture repairs; separate branch and draft PR | Live Staging and WORK/Opus/Rx/orthodontic branches were inspected as boundaries, not merged. Library v2 download was blocked by proxy403; its bytes and prior67-test claim were not verified. No verified Gemini patch was incorporated. |
| Delivery and deployment | Reviewable branch, source tests, generated native schema artifacts, browser screenshots and draft PR | No merge, deployment, real patient operations or external messages. CI, separate target composition and authorized Staging acceptance must be assessed independently. |
