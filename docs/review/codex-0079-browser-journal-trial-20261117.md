# Retired 0079 journal recovery: synthetic browser trial

Base `a96017d9840a91c48b93f52a06bb1ae9e4d1bd26`. Independent local review branch; no merge or deployment. All accounts, patients, commands and PostgreSQL databases in this test are synthetic. The harness creates uniquely named identity-checked databases through the existing backup fixture and starts a local Next development server. It does not use the security-HTTP global setup, which drops a fixed-name database.

The limited witness bundles the real `OrthoFollowupCoveragePanel`, real React, SessionProvider and financial journal into a synthetic page. A browser creates the unresolved historical command using the actual `reserveFinancialCommand` and IndexedDB implementation. The component uses a real authenticated request to the application server and an identity-checked fresh PostgreSQL database without migration 0079. The PUT returned HTTP **503 `coverage_not_ready`**. The test verifies the exact original body and a single PUT, no POST, identical journal and revision, no call to acknowledgement or `onSaved`, unchanged financial, audit and adjustment rows, no 0079 tables or registry row, and no subsequent DDL. An esbuild observer wraps but delegates to the actual acknowledgement function.

Targeted run: **1 passed, 1 skipped**. The skipped case was excluded by the name filter; it must not be represented as passing. The Next server was development mode; this is a real component/browser/IndexedDB/HTTP/PostgreSQL witness, not a built-app acceptance or full patient-page journey.

A separate full patient-page attempt was run twice. After successful authentication and journal seeding it could not find the case-navigation button; the patient page was blank under this local development server. Both runs failed before reaching the PUT, so they establish neither success nor an application defect. Its original failing witness remains in the test file. Diagnosing the blank page and rerunning the full built-app patient journey remain open. This evidence changes no clinical or orthodontic workflow and does not establish CI, release, or production readiness.

## Follow-up: patient page and browser-safe intake boundary

On the first two local patient-page attempts, navigation failed before the status request. A subsequent diagnostic run recorded only bounded status/DOM counters and error classes, never response bodies: `/patients/1` returned 500 and Next reported `ModuleBuildError`, with `UnhandledSchemeError` and `node:crypto`. Static browser dependency tracing found `app/patients/[id]/page.tsx → components/patient/SummaryTab.tsx → components/patient/PatientIntakeHistory.tsx → lib/portal.ts → node:crypto`. The portal page also imported the same server module for intake definitions. This was reproduced under `next dev --webpack`, and the focused browser-bundling checks failed **2/2** before the change.

The independent fix commit `f844e6ed88a927f1fb54c55acea3a5174fa8b5e1` moves only the original intake condition list and its type into a pure shared module; the server module re-exports the same public values and retains the existing token implementation. Both browser consumers now import the pure module. The focused boundary and original portal unit suites passed **15/15**; a separately invoked esbuild browser bundle of the patient-page graph completed. This does not establish a full Next production build: CI run 44015100378 reported the default Turbopack Production build successful for a descendant with unchanged production source, whereas our reproduced error used Webpack development mode. The hosted run as a whole was not assumed successful.

With that fix the patient page loaded and the case-list toggle appeared. Two later attempts still failed before accessing details: the browser case-list request was aborted while an independently authenticated warm-up read returned 200 and contained the synthetic case. The final run prewarmed the real case-list and case-detail endpoints to avoid cold development compilation; it used the existing case-list refresh button once if the initial 12-second test wait found no detail. It did not change the product's 8-second timeout. The selected **full patient-page browser case passed 1/1**, with the separate isolated witness skipped by the test-name filter: after actual login and navigation it sent the original command in one real PUT, received **503 `coverage_not_ready`**, retained the entire journal including revision, showed no saved notice, sent no POST, preserved the checked financial, audit and adjustment snapshots, and performed no DDL. The fixture's database had neither the 0079 migration row nor its coverage tables. The old unsuccessful runs are not recast as passing, and the test remains enabled.

This evidence uses Next development mode, not a standalone production build; no fresh production build, full CI, or release acceptance is claimed. The limited component witness described above is independent of the patient-page run. No response body was logged; only the expected 503 JSON code was asserted in memory.
