# Restore effective target guard: WIP

The administrative drill used to compare the apparent URL host against only one application URL before constructing a pg client from the original URL. Query parameters understood by pg can override that host, and a loopback-looking URL could also affect the TLS decision. This change rejects ambiguous connection strings and inherited pg options, checks all four configured application database URL aliases, and supplies one issued immutable configuration to reset and staged restore. Current process aliases and pg options are checked again before removing the prior stage and before constructing each client. Direct staged restore uses the same checks.

The accepted target grammar is intentionally narrower than general pg URLs: it requires explicit user, port and an ASCII database name, and rejects target query parameters except a single `sslmode=disable` for a literal loopback. Runtime aliases with unsupported forms are refused rather than silently ignored; blank aliases are ignored. Defined `PG*` environment variables are rejected except the application's two trusted CA settings. These restrictions can reject formerly accepted deployments and require compatibility review before rollout. A direct dependency on the pg URL parser is pinned through the lockfile; tests compare accepted synthetic identities with the installed pg Client without connecting.

The guard cannot establish that different DNS names or IP addresses refer to different servers, and does not eliminate changes after the last synchronous check or while stage removal is in progress. It is not an isolation or authorization guarantee for a target, nor a proof of safety for a populated database. A rejected operation retains the prior stage only when refusal occurs before stage removal. The snapshot pins the client configuration, not DNS resolution.

Unit tests use synthetic URLs, archives and mocks. No real database, TLS handshake, end-to-end restore, deployment or production environment was exercised by this change. The existing open issues about historical migration compatibility, sequence behaviour, and CI remain separate.
