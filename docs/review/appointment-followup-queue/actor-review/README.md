## Actor binding

On published cdd9a320, hold actor A's successful context GET response, switch the shared browser cookie to B, then release the response. A's never-submitted persisted intent was accepted as B: the red browser test expected 409 but received 201. Checking a separate GET did not bind the later POST.

New commands include a required positive expectedActorUserId witness. After the existing account/source/task/reset locks and canonical session revalidation, the writer compares it with the authenticated transaction actor before receipt replay or any mutation. The supplied actor never authorizes access or selects the authenticated identity. Web Lock coordination remains intact. Missing witnesses are refused, rather than silently bound to whichever cookie arrived.

The receipt namespace already includes the authenticated actor. The new witness is deliberately excluded from the existing version-1 intent fingerprint so historical fingerprints do not change. Pre-witness local intents remain byte-for-byte in storage; the reader binds their network replay to the original actor-specific slot owner, adding only this witness. It never binds them to a replacement cookie. A witness that disagrees with the slot owner fails closed. New attempts persist the witness before sending. Compare-before-delete continues to compare the exact stored bytes. This compatibility path preserves the old semantic intent/request key and historical receipt replay; it does not rewrite old database history.

The held-GET browser case now requires 409, unchanged A-owned persisted evidence, zero task writes, and one event only after switching back to A and retrying. PostgreSQL also tests foreign-actor rejection before creation and after a committed receipt, plus normal same-actor replay. Existing two-editor/two-tab lost-response tests remain required.

## Remaining acceptance blocker: expired uncommitted attempts

The browser characterization reproduces an uncommitted persisted command whose dueAt has expired. Both retries return FOLLOWUP_DUE_MUST_BE_FUTURE; Refresh preserves identical bytes, no task is created, and there is no fresh-create action. This is a real workflow blocker, not a completed recovery feature. No unsafe local deletion is added.

A bounded safe design requires a durable, append-only retirement proof keyed by the same actor/request identity and bound to the canonical intent fingerprint/source/generation. Retirement must acquire the same shared reset fence and actor/request advisory lock as saving, then revalidate the actor/source/generation and check the receipt while serialized. If a save won the lock and committed, return committed and retain exact replay. If retirement wins with no receipt, atomically persist the retirement proof; EVERY future writer of that identity must reject it after acquiring the same lock. A missing receipt alone is never proof: the durable tombstone is what prevents a previously delayed request from later committing. Repeating retirement must return the same proof; rollback/lost response must remain recoverable. Only a matching acknowledged proof can allow the UI, under its Web Lock, to compare-delete its exact slot and create a NEW request ID with a fresh due time.

This needs separately reviewed numbered storage, immutable/reset/export/restore classification and collision/concurrency tests (save-first, retire-first, held writer, lost retirement reply, wrong actor/source/generation, key/fingerprint mismatch, restored receipts). The existing schema has no such durable retirement fact. This slice does not assert concurrency safety for a partial implementation and does not add a momentary no-receipt endpoint. Recovery remains an explicit acceptance blocker pending that protocol, rather than extending history semantics without proof.
