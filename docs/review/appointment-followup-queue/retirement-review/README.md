# Expired attempt retirement review

The bdc0707 browser characterization established that an expired, never-submitted durable command could only repeat `FOLLOWUP_DUE_MUST_BE_FUTURE`. Refresh correctly preserved evidence but could not recover the workflow. The existing 0068 collection retirement table cannot safely serve this operation: it is keyed globally for payment/installment operations, has a live patient FK and a different reset contract, and fences financial receipt writers rather than appointment event/receipt writers. Reusing it would require changing finance semantics and would not preserve the appointment actor/source/generation namespace. Only its durable fence pattern is reused in an isolated additive table. This change adds an explicit server-authoritative retirement operation; it never infers non-commit from a momentary missing receipt.

POST `/api/appointments/[id]/followup/retire` accepts the exact saved command. It shares the mutation's reset fence, actor/request advisory lock, source/task/live-link locks, canonical session/role/actor witness checks, patient access, source identity and generation guards. An existing matching receipt returns `committed` and preserves exact replay. An existing matching retirement returns its same proof. Otherwise only an expired open command with the current source/revision may retire. The transaction records an immutable actor/key/fingerprint/source/generation tombstone and audit event. Future saves of that identity fail closed. New database event/receipt insert fences also reject a retired identity, including an older application writer; retirement itself refuses any event or receipt for that identity. All key checks serialize with the same lock. A transaction rollback removes both tombstone and audit, so there is no partial acknowledgement.

The UI keeps its exclusive Web Lock and raw persisted bytes throughout this operation. Lost replies, non-success responses, wrong actor/key/fingerprint, and `committed` outcomes retain the slot. Only a matching authoritative `retired` acknowledgement permits compare-before-delete of the exact bytes. A fresh command requires an explicit user action and a new request ID. This endpoint deliberately does not retire commands after source, generation, revision or live-link changes; those continue to fail closed rather than bypassing stale-source protection.

Additive migration 0072 was allocated after checking repository PRs through #447 (no competing numbered migration). Numbered/runtime bytes match. Published 0070 and 0071 remain unchanged. Retirement history has no live patient/appointment FK and belongs to the reset KEEP set, alongside task/event/receipt history. Actual reset and archive restore tests preserve nonempty retirement proofs and prevent retired-key reuse. The registry, PostgreSQL schema contract and disclosure were regenerated; count changes in older fixture tests only account for the additive tail.

Synthetic proof covers: expired never-submitted commands; repeated/lost retirement acknowledgements; mismatched acknowledgement; committed response loss followed by exact replay; a save queued ahead of retirement on the shared key fence; retirement before a late writer, including transaction rollback of its tentative task update; role/actor/source/generation rejection; immutable history; real reset and backup restore. Existing two-editor/two-tab lost-response retry tests remain part of the built-browser suite.

This adds triggers to existing event and receipt tables using ordinary transactional DDL. Installation can wait for locks and block conflicting writers; no production contention or zero-interruption guarantee is claimed. There is no migration-local lock timeout.
