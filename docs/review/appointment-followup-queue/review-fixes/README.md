# Independent review follow-up

## Durable retry ownership

On 090dae60, two editors/tabs mounted at one revision could replace the durable slot after the first save committed but its response was lost. A second revision conflict and Refresh could then erase the first attempt. The server revision guard still prevented duplicate events; the durable client evidence was defective.

Red-before: both real-browser cases fail at the exact persisted-body assertion. Green-after: the same two cases pass, along with the existing follow-up HTTP/mobile cases (4/4). They delay advisory notifications deliberately, hold the first real POST response after commit, click the stale editor while it is in flight, then drop the reply, reload and replay. The two-tab case also replaces the session cookie before the stale UI refreshes: the other actor cannot replay or clear the original actor's slot; switching back recovers it. Only the creation and one update event exist.

The editor now takes an origin-wide exclusive Web Lock (actor/patient/appointment) across context revalidation, read/persist/send and acknowledgement. Busy locks do not queue stale clicks. No unlocked/localStorage-lock fallback exists. A stale editor adopts the existing intent and asks for explicit replay. New intents re-read server revision before persistence. Successful receipts permit only compare-before-delete of the exact bytes; 400/404/409 never delete evidence. Refresh preserves it. Same-document/custom and cross-tab/storage events improve UI only, not correctness. Malformed evidence remains untouched and blocks new intent.

Unknown/irrecoverably stale attempts deliberately remain blocked for review; there is no client-side cancellation/retirement proof in this slice. Unsupported Web Locks or failed durable storage blocks submission.

## Bounded query work and additive 0071

The original 090dae60 query timed out after 8,003 ms for the global page and 15,001 ms for the sparse-patient page with 10,000 current tasks and 10,000 unrelated visits/planned rows. `query-before.json` records these local timeouts and estimated plans, not invented actual row counts: the original plan nested a planned-visit scan inside a clinic-wide visit scan.

The eligibility expression now probes direct visits separately and then source-linked planned rows. Scalar `LIMIT 1` probes prevent the optimizer from hashing the entire visit/status history before a small page. Rules for inverse/direct-null planned links, clinical attendance, moved pointers and stale source protection remain covered by the existing PostgreSQL tests. The queue binds the current generation already read inside its reset fence.

Migration 0071 adds four measured indexes: generation/due/id for open tasks, direct appointment and planned-session visit links, and inverse planned appointment links. It builds the generation index before retiring 0070's feature-owned unscoped due index. An intermediate query scanned 50,000 old-generation rows when that predecessor was retained; the later actor-review recreate-after-migration experiment selected the new index, but did not test retaining the original predecessor through upgrade. The later true-retention upgrade nevertheless selected the original index and filtered 50,000 old-generation rows. Simple DROP removal is therefore insufficient. A separate unpublished bounded key-page query plus retention candidate passed actual-plan and reader/writer lock diagnostics; do not apply it or rewrite 0071 without deployment provenance. Existing planned-session and patient-appointment indexes are reused. No speculative link index was added; the sparse-patient plan uses the existing patient appointment index, unique task source and link primary key.

The canonical PostgreSQL test applies 0071 to a populated 0070 database, checks byte-identical runtime/file registration, hashes clinical/task/link/event/receipt facts before and after, verifies idempotent registration, and proves complete transactional rollback on a conflicting index name. Published 0070 bytes are unchanged. Latest repository PRs through #444 were checked before allocation, then rechecked through #445 before publication; #442, #444 and #445 contain no numbered migration. This reservation is separate from other candidates: #443 requires its own 0070 followed by 0071, and composition with independently advanced migration chains must be reviewed before integration. Never overwrite an occupied number or silently reinterpret a registered checksum.

`query-performance.json` contains actual `EXPLAIN (ANALYZE, BUFFERS)` output and SQL/migration hashes for 10,000 current tasks, 50,000 retained old-generation open tasks, and 10,000 each of visits, planned visits, treatment sessions and status events. First/next/sparse-patient execution measured 0.648/0.526/0.787 ms in this run. Both global pages read exactly 26 task index rows and filtered zero old-generation rows; clinical probes use indexes, with at most two rows per loop asserted. Sparse-patient returns 20 blocked linked records without scanning unrelated clinical history. The ordinary transactional DDL took 92.8 ms locally. These figures do not predict production lock waits or latency: `CREATE INDEX` can block writers during construction; ordinary `DROP INDEX` can take ACCESS EXCLUSIVE on appointment_followups and block both reads and writes. Runtime application has no migration-local lock_timeout. The 92.8 ms isolated timing and collision rollback test are not contention or zero-interruption evidence. Integration requires a separately reviewed deployment plan; see actor-review for the safer retention experiment. No Production load or operations occurred.
