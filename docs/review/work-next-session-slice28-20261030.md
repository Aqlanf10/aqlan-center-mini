# الشريحة 28 — حجز الجلسة القادمة من الزيارة

الأساس المقبول: `27f0818fb143569324772290424dd7c903d4c2da`، فرع كلاود `feat/work-recovery-followup-20261027`. قَبِل الأب شاشة الصالة بعد نجاح [CI 41114221748](https://github.com/Aqlanf10/aqlan-center-mini/actions/runs/41114221748)، وأذن باستكمال `visits/[id]/next` وفق HANDOFF. نجاح الرأس السابق لا يغطي هذه الدفعة. لا نشر أو تفعيل أو دمج main؛ لا هجرات أو بيانات/صلاحيات حقيقية.

## الإثبات قبل الإصلاح

الاختبار المبني الاصطناعي `canonical-next-session-journey` فشل على بناء الرأس السابق: تسجيل الدخول والسياق السريري نجحا للحساب المخوّل، لكن POST أعاد **401 بدل 201**. السجل `baseline-http.log` محفوظ. هذه فجوة نقل canonical مثبتة، وليست ادعاء حادثة إنتاج أو تسريب جديد. كذلك أعاد اختبار PostgreSQL على مسودة الشريحة غير المنشورة إنتاج deadlock `40P01`: حجزان بيومين متباعدين يمسكان SHARE على ملف واحد ثم يملآن هاتفه الفارغ. أُصلح باستباق الكتابة بـ`FOR UPDATE NOWAIT` بدل ترقية قفلين مشتركين؛ يحفظ التعارض الصريح وقابلية المحاولة الجديدة بعد التحقق. سجل الفشل وبصمة المسودة وفرق الإصلاح محفوظة. فحوص نطاق الحجز لنفسه انحدار للحد المقبول سابقًا، وليست ادعاء إعادة إنتاج ثغرة جديدة في الإنتاج.

## العقد والتنفيذ

- `lib/canonical-next-session.ts` و`app/api/visits/[id]/next/route.ts`: اختيار ظرف الهوية مرة واحدة، لا fallback من canonical إلى legacy، ردود عربية و`no-store` وحد الجسم القائم. `appointments.create`، نطاق مرضى غير `none`، ونطاق مواعيد غير `none`. الخارج يساوي المفقود 404. مع نطاق المواعيد `own` يجب أن يكون الطبيب المسؤول الحالي هو طبيب الحساب؛ دور admin لا يمنح تجاوزًا.
- قبل الكتابة: تحقق أولي ثم قفل نافذة الأيام الثلاثة بالقفل المشترك للحجز، ثم صف الزيارة وإعادة إثبات الجلسة. نطاق الملف يُثبت **قبل** ملء الهاتف أو ربط زيارة المشي. الشهود الموجبة للنطاق والمسؤولية تُقفل بـNOWAIT كي لا يعكس الكاتب ترتيب أقفال العمليات السريرية. انتظار اليوم أو صف الزيارة أو الخدمة يتبعه إثبات سلطة جديد، ويعيد runtime الإثبات قبل commit.
- `prepareNextSessionPatient` يستخدم نفس محلل الملف مع callback قبول قبل أي أثر. `createNextSessionWith` هو جسم الكاتب القديم نفسه بلا `ensureSchema` داخل المعاملة القانونية؛ الغلاف القديم يفوض إليه. `resolveServiceByLegacyTypeWith` يتيح القراءة على الاتصال نفسه. السعة والخدمة وحجب الطبيب وسياق الحالة وكتابة الموعد وتدقيقه على اتصال المعاملة؛ فشل الحكم أو التدقيق يرجع الآثار كلها.
- المصدر هو الزيارة أو حالة مرتبطة بها يثبتها المحلل القائم، وبصمة مسؤولية راجعها الموظف؛ doctorId المرسل لا يستبدل المسؤول. لا تغيير في تداخل المريض أو تحذير الموعد القريب أو السعة أو تفسير خارج الدوام. التجاوز يحتاج `appointments.override-capacity` وسببًا، ويُسجّل مع `appointment.create` ذريًا.
- الزيارة بلا ملف لا تمنح ربط ملف خارجي لمجرد أن doctor_id فيها هو الموظف. مطابقة الهاتف لملف مشروع لا تحتاج `patients.create`. إنشاء ملف جديد فعلًا يحتاج هذه القدرة، وفق حد تأكيد طلبات الحجز في الشريحة 21؛ إذا غاب السياق السريري تبقى النتيجة رفضًا ويتراجع الملف الجديد، حتى للمالك. لا اختراع مسؤول سريري أو توسيع نطاق بالحجز.
- `CanonicalNextSession` في ملف المريض وقائمة اليوم للزيارات المنتهية المرتبطة بملف. يبقى تصميم المركز، و390px بلا تمرير أفقي. موظف الحجز لا يحتاج إدارة النداء أو كشف التفاصيل السريرية كي يستخدم مدخل قائمة اليوم. كل القراءات والأوامر المستخدمة منقولة؛ لا تشغيل checkout المالي القديم ضمن هذه الشريحة.

## إعادة المحاولة وضياع الرد

لا يوجد مفتاح طلب دائم أو رابط موعد عودة وحيد في المخطط الحالي، ولم تُضف هجرة. طلبان مطابقان في الوقت نفسه يتسلسلان وتمنع قاعدة تداخل المريض الثاني؛ حجز وقت آخر قريب يحتاج تأكيدًا جديدًا. هذا ليس exactly-once بعد إلغاء الموعد الأصلي أو في اقتراح بعيد جديد.

قبل إرسال POST تحفظ الواجهة في sessionStorage علامة خاصة بالحساب/المريض/الزيارة وتوقيت الاقتراح والطبيب/المدة فقط؛ لا أسماء أو هواتف أو بصمات سياق أو توكنات. هذه العلامة ليست صلاحية أو إثباتًا من الخادم. الرد الضائع/5xx/نجاح غير متحقق يقفل النموذج، ويظل القفل بعد إعادة تحميل التبويب. قراءة ملف المريض تُثبت الوصول الحالي والمواعيد: وجود موعد مطابق يُعرض كموعد موجود، دون نسبة جازمة إلى الطلب الضائع؛ عدم ظهوره يحتاج إقرار نية جديدة منفصلًا قبل نموذج حجز جديد. لا إعادة تلقائية. عند عدم توفر تخزين المتصفح يبقى قفل الحالة داخل المكون فقط؛ لا وعد بمنع دائم عبر جلسة متصفح جديدة.

PG يغطي المالك والأدوار، `none/own/all`، المطابقة للمفقود، ملف مشي خارج النطاق قبل الربط، مصدر خاطئ/متغير/مغلق، نطاق المواعيد، السباق، التأكيد القريب، حجب الطبيب، التجاوز بتدقيق ذري وفشل تدقيقه، انتهاء الجلسة بعد انتظار **قفل فعلي مثبت** لليوم وللزيارة، تبدل علاقة المريض أثناء الانتظار، تسلسل سحب الصلاحية خلف العملية المقبولة ثم رفض الطلب اللاحق، وقراءة سياسة السعة بعد الانتظار. pool باتصال واحد يثبت عدم طلب اتصال خفي داخل الأمر.

HTTP والمتصفح يغطيان الرفض والجلسة المسحوبة، عدم تسرب وجود زيارة خارج النطاق، الزر حسب القدرة، الطبيب الحالي والتأكيد القريب، قائمة API محصورة، شاشة 390px، ضياع رد بعد commit وإعادة تحميل الصفحة، وفشل نقل قبل وصوله للخادم ثم قراءة وتأكيد نية جديدين. توجد [لقطة اصطناعية](evidence/work-next-session-slice28-20261030/next-session-390.png).

لم تُشغّل محليًا حزمة PostgreSQL أو HTTP الكاملة؛ CI للرأس المنشور هو الفحص الكامل المطلوب. أُصلحت أثناء إعداد الاختبارات أخطاء استيراد وبيانات fixture، ومنها اسم القدرة الكامل وحالة إغلاق الحالة السريرية واستعادة النطاق في fixture، وافتراض اختبار خاطئ بأن خارج الدوام منع مطلق. لم يُعدّل المنتج لتحويل تحذير الدوام إلى منع، ولم تُضعف العتبات أو الاختبارات القائمة.
