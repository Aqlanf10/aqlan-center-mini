الأساس المقبول `bc4397460efdc10f00b6efe98230100425d6ec43`، فرع Claude `feat/work-recovery-followup-20261027`. أكّد الأب قبول الشريحة 28 بعد نجاح [CI 41127011500](https://github.com/Aqlanf10/aqlan-center-mini/actions/runs/41127011500)، وأذن باختيار أصغر عقد تالٍ من ortho/ceph/plans حسب HANDOFF §5.3. الرأس البعيد طابق الأساس قبل التنفيذ. لا دمج أو نشر أو تفعيل أو بيانات حية، ولا تعديل مرشح #495 أو الفروع المستقلة.

## النطاق والاعتماديات

نُقل **GET `/api/ortho` وحده** مع قسم ملخص عند الطلب داخل ملف المريض القانوني. ليس نقلًا لوحدة التقويم كاملة أو شاشة متابعتها أو كتاباتها. صف الخريطة يفرض `clinical.ortho.view` ونطاق المريض؛ لا قرار صلاحية جديد. تعتمد القراءة على `runCanonicalReadSnapshot` و`readCanonicalPatientRecord` وشرط المرضى المركزي نفسه، وعلى أعمدة الحالة والطبيب الموجودة. لا هجرة أو جسر سريري أو علاقة علاج أو سياسة مالية جديدة.

قُرئت AGENTS.md وHANDOFF وخريطة المسارات وتعليمات Next.js المثبت وDESIGN.md. لم يوجد مجلد `.agents/skills` في الشجرة أو موضعه البديل في workspace؛ الدليل المحلي الموجود `docs/skills/clinic-leadership/SKILL.md` يخص مساحة القيادة، وليس سياسة التحويل السريري. لم يُستخدم لتوسيع النطاق.

## الإثبات قبل الإصلاح

رحلة HTTP مبنية على الرأس المقبول: تسجيل الدخول وقراءة ملف المريض نجحا، لكن حسابًا له `clinical.ortho.view` ونطاق `own` تلقى **401 بدل 200** من قراءة حالات مريضه. الدليل `baseline-http.log`. هذه فجوة قبول canonical مثبتة، وليست ادعاء تسريب أو حادثة إنتاج.

## ما تغيّر

- `app/api/ortho/route.ts`: اختيار مغلف الهوية مرة واحدة؛ canonical لا يسقط إلى legacy. قراءة JSON لا تُخزّن، ورسائل الرفض عربية محدودة. فرع GET القديم وجسم POST القديم محفوظان.
- `lib/canonical-record-reads.ts` و`lib/canonical-ortho-reads.ts`: تسجيل `read:ortho.cases` بالقدرة ونطاق المريض. `patientId` اختياري موجب منفرد؛ لا معلمة طبيب أو مال أو حالة يمكن استعمالها لتغيير النطاق. خارج النطاق مطابق للمفقود 404؛ المريض المسموح بلا حالة يعيد قائمة فارغة سليمة.
- `listOrthoCaseSummariesWith` في `lib/db.ts`: قراءة واحدة على اتصال اللقطة، وتصفية SQL قبل حد 300. صف إضافي مسموح فقط يثبت `hasMore`. القائمة العامة للحالات المفتوحة؛ فلتر المريض يحتفظ بالحالات المغلقة وترتيب تاريخها، دون إصلاح أو إعادة ربط تاريخ قديم.
- الإسقاط allowlist صريح: معرفا الحالة والمريض واسمه، الجهاز والفك، الحالة والمرحلة المسجلة، البداية والمدة المخططة، الأسلاك المسجلة، الطبيب المسؤول، وعلامة العلاج السابق للنظام. لا ملاحظات سريرية أو سجل شدّات أو صور أو خطط أو معلومات تمويل. المالك يستعمل التمثيل المختصر نفسه دون تغيير صلاحياته الأساسية. الملخص لا يدّعي تمثيل سجل الحالة الكامل.
- `lib/ortho.ts`: أنواع العرض فقط؛ حسابات التقويم وقواعده لم تتغير. المسؤول المسجل لا يُستبدل بالمستخدم الحالي. نطاق `own` يحتفظ بكل شهوده القائمة، ومنها المسؤولية الفعلية لحالة تقويم نشطة؛ لقب المدير لا يمنح جميع المرضى.
- `CanonicalOrthoCases` داخل `CanonicalPatientProfile`: قسم مطوي حتى يطلبه المخوّل، ولا يركب محررًا قديمًا أو يستدعي مسارات الصور أو المال. 390px وRTL والهوية الحالية. يتخلص من البيانات عند التحديث/الخطأ/الإخفاء، ويُبطل الطلب السابق، ويعيد القراءة عند التركيز والظهور وكل 30 ثانية ما دام القسم مفتوحًا ظاهرًا؛ مهلة 8 ثوانٍ. لا رد متأخر يعيد محتوى أقدم.

## التزامن والحدود

القراءة لقطة REPEATABLE READ READ ONLY مملوكة واحدة تشمل قبول الجلسة والمنح والنطاق والبيانات. تختبر الجولة الانتظار الحقيقي خلف سياج دورة الهوية، انتهاء الجلسة خلاله، وسحب المنحة قبل تحريره. نقل المريض وتغيير السلك على اتصال آخر لا يخلطان القديم بالجديد؛ الطلب اللاحق يحترم النطاق الجديد. فشل قراءة المصدر يرفض النتيجة كلها ويترك اتصالًا صالحًا للطلب التالي.

هذه شريحة قراءة، لذلك لا أمر تعديل جديد ولا أثر يحتاج سجل تدقيق كتابي ذري. أثبتت الاختبارات عدم تغيير عدد الفواتير والجسور وسجل التدقيق. حفظ كتّاب التقويم وقيود علاقاتهم القديمة تؤكده اختبارات الهوية والتاريخ القديمة. فحص حد الحجز لنفسه من الشريحة 26 أُعيد كاختبار انحدار؛ لم يتغير الشرط المركزي.

قيود الشريحة 28 باقية: لا durable idempotency؛ غياب sessionStorage لا يضمن الاستعادة بعد reload. هذه الشريحة لا تعمم ذلك الضمان ولا تعدله. جودة صوت شاشة الصالة على جهازها الحقيقي غير مثبتة، وهي مستقلة عن هذا العقد.
