# تحصين أمن طبقة التطبيق/HTTP — P2

هذه الوثيقة تشرح **قرارات** أمن P2 لا تكرر الكود — لماذا اختير كل قرار، وما
الذي يُثبته، وما الحدود الصادقة لما لا يُغطى. كل قرار له اختباره المُلزِم:
وحدات في `npm test`، وتكامل PostgreSQL في `npm run test:postgres`، واختبارات
HTTP حقيقية على التطبيق المبني في `npm run test:security-http` — والثلاثة
بوابات إلزامية في CI لا اختيارية.

**الحالة: بوابات أمن P0 + P1 + P2 ناجحة — بانتظار تفعيل الإنتاج النهائي
(Final Production Activation).** لا تُكتب عبارة «Production Ready» بعد P2:
يفصلنا عنها قرار تشغيل بشري واعٍ (migration للإنتاج + نشر مدقق)، لا سطر كود.

## 2) رؤوس الأمن الثابتة (S2)

- `X-Content-Type-Options: nosniff` — على كل المسارات بما فيها الأصول الساكنة.
- `Referrer-Policy: no-referrer` — لا عنوان مصدر يخرج من التطبيق الطبي.
- `X-Frame-Options: SAMEORIGIN` مع `frame-ancestors` (القرار في §4).
- `Strict-Transport-Security: max-age=31536000` **في الإنتاج فقط** — قيمة
  محافظة عمدًا بلا `preload` وبلا `includeSubDomains`: الأولى قرار لا رجعة
  فيه عمليًّا على مستوى النطاق، والثانية تنتظر إثبات ملكية كل النطاقات
  الفرعية — ولا واحد منهما متحقق.
- `Permissions-Policy` محافظة: `microphone=(self)` (التسجيل الصوتي للرسائل
  ميزة فعلية — لم تُمنع كليًّا بل قُيّدت بنفس الأصل)، و`camera=()` (لا ميزة
  تستخدم الكاميرا اليوم — فتُغلق، وإن ظهرت حاجة حقيقية تُفتح بمبدأ least
  privilege مع توثيق)، و`geolocation=()` و`payment=()` و`usb=()` و
  `browsing-topics=()`.
- `Cross-Origin-Opener-Policy: same-origin` و
  `Cross-Origin-Resource-Policy: same-origin`.
- **لا COEP عمدًا**: تتطلب من كل الموارد المضمنة CORP/COEP، وتكسر تحميلات
  مشروعة (صور خارجية/عاملات) بلا مكسب ملموس لتطبيق intranet لا يضمّن
  موارد الطرف الثالث أصلًا. القرار موثَّق هنا لا صامتًا.
- `poweredByHeader: false` — لا `X-Powered-By` (اختبار HTTP يفشل إن عادت).

المصدر الواحد `STATIC_SECURITY_HEADERS` تقرؤه اختبارات الانحدار فيفشل CI
إن اختفت أي ترويسة.

## 3) CSP بـnonce (S3)

- **البناء**: `lib/csp.ts` (`buildCspHeaderValue`) — مصدر واحد للمصدر
  والاختبارات. `proxy.ts` يولّد `crypto.randomUUID()` **لكل طلب** ويضع
  السياسة في ترويسة الطلب (فيطبّقها Next على سكربتاته المتولدة) وفي
  ترويسة الرد (فيُلزم بها المتصفح).
- **الإنتاج**: `script-src 'self' 'nonce-…' 'strict-dynamic'` — لا
  `unsafe-inline` ولا `unsafe-eval` إطلاقًا. `style-src 'unsafe-inline'`
  مقصودة: Next/Tailwind يحقنان أنماطًا داخلية، والأنماط ليست متجه الهجوم
  الذي يحميه nonce هنا.
- **التطوير فقط** يضيف `'unsafe-eval'` (يتطلبها React Refresh).
- `connect-src 'self'`: لا اتصال خارجي من المتصفح — لا تحليلات ولا خطوط
  خارجية ولا CDN.
- `worker-src 'self' blob:` و`manifest-src 'self'` و`media-src 'self' blob:`
  (تسجيل الصوت) و`img-src 'self' data: blob:` — تختبرها HTTP فعلًا على
  صفحات حقيقية (السكربتات المولدة تحمل nonce يطابق ترويسة CSP، وكل طلب
  صفحة يبني nonce مختلفًا).
- `upgrade-insecure-requests` في الإنتاج.

## 4) قرار iframe (S3/S2)

فحص الكود وجد استخدامًا إنتاجيًّا واحدًا: معاينة PDF داخل لوحة الطاقم عبر
`<iframe src="/api/documents/{id}">` (components/PatientDocuments.tsx) —
تضمين **نفس الأصل** لمسار API واحد. القرار:

- كل الصفحات: `frame-ancestors 'none'` — لا أحد يضمّن لوحة الطاقم أو
  صفحات المرضى، وX-Frame-Options: SAMEORIGIN طبقة ثانية.
- مسار المستندات `/api/documents/{id}` وحده: `frame-ancestors 'self'` —
  سماحٌ لنفس الأصل حصرًا (لا أصل خارجي، لا wildcard) — عبره تعمل معاينة
  الطبيب كما كانت.
- لا wildcard framing في أي حال، واختبار HTTP يتحقق أن مسار المستندات
  يسمح `'self'` وأن كل ما عداه `'none'`.

## 5) الكوكيز وSameSite (S4)

**القرار: `SameSite=Lax` في الإنتاج للطاقم والبوابة معًا، بلا `Partitioned`.**

الوضع السابق كان `SameSite=None; Partitioned` «للمحاكي/iframe» — فحص الكود
لم يجد أي iframe خارجيًّا يضمّن التطبيق؛ الاستخدام الوحيد (معاينة PDF)
نفس-الأصل ويعمل مع Lax تمامًا. None كان يفتح نافذة CSRF من الجذر: الكوكي
ترسل مع كل طلب فرعي عابر للمواقع.

- كوكي الطاقم: HttpOnly + Secure (خلف HTTPS) + Path=/ + Lax. خروج الطاقم
  يطابق سمات الدخول حرفيًّا (اختبار انحدار على المصدر + HTTP).
- كوكي البوابة: نفس القرار تمامًّا.
- **Bearer منفصل عن الكوكي**: عملاء بلا متصفح (مزامنة/تكامل) يمرّون عبر
  `Authorization: Bearer` — مسار معتمد وموثق، والتوكن لا يُرسل تلقائيًّا من
  موقع آخر فخطر CSRF لا ينطبق عليه. هذا هو الفصل المطلوب بين تدفق المتصفح
  (كوكي) وتدفق API (Bearer).

## 6) حارس الـmutations — CSRF/Origin (S4)

حارس واحد في `proxy.ts` لكل POST/PUT/PATCH/DELETE على `/api/*`:

1. **Bearer ⇒ يتخطى الحارس** — RBAC/BOLA كاملان في المسار نفسه.
2. **`Sec-Fetch-Site: cross-site` ⇒ 403** — ترويسة يكتبها المتصفح وحده.
3. **Origin معلن**: يجب أن يطابق مضيف الطلب (أو قائمة `TRUSTED_HOSTS`) —
   وإلا 403. لا نثق بترويسة Host إلا عبر `TRUSTED_HOSTS` أو مطابقة الأصل
   نفسه.
4. **كوكي بلا Origin ولا Sec-Fetch-Site ⇒ 403 (fail-closed)**: متصفح حديث
   يرسل Origin دائمًا على الطلبات التي تغيّر الحالة؛ غيابه مع كوكي يعني
   عميلًا اصطناعيًّا بكوكي منسوخ — وعملاء البرنامج لهم مسار Bearer.
5. **المسارات العامة** (دخول/إعداد/بوابة/حجز/وصول): نفس قواعد 1–3، أما
   الطلبات بلا متصفح (curl/native) فتصل المسار — حمايتها حدود المعدل والحجم
   والنوع داخل المسار (S5/S8/S10).

اختبارات HTTP الحقيقية تغطي: cross-site مرفوض، أصل غريب مرفوض، كوكي بلا
أصل مرفوض، أصل ملغوم مرفوض، same-origin يعبر، الخروج محمي بنفس الحارس،
Bearer يعبر.

**CSRF Token؟** لم يعد ضروريًّا: Lax يمنع إرسال الكوكي أصلًا عبر المواقع،
والحارس يمنع الطلب من أصل غير موثوق. لو اضطررنا مستقبلًا لـNone لميزة
تضمين حقيقية، فالحل الموثق: كوكي منفصل ضيق المجال + CSRF Token موقّع مرتبط
بالجلسة يُرسل في ترويسة (لا query string أبدًا) — لم نحتج إليه اليوم فلم
نبنِه.

## 7) CORS (S6)

**لا CORS إطلاقًا — same-origin افتراضيًّا.** لا ترويسة
`Access-Control-Allow-Origin` تُرسل لأي مسار، ولا انعكاس لأصل العميل، و
`OPTIONS` (preflight) لا يمنح وصولًا ولا يفتح قائمة. أي تكامل مستقبلي
(mobile/native) له مسار Bearer؛ ولو احتاج origin متصفح خارجي فالقرار
المستقبلي الموثق: allowlist صريحة لمسارات محددة — لا `*` ولا انعكاس أعمى،
وكل مسار يبقى يطبق الجلسة/RBAC مهما سمح CORS.

## 8) بوابة SSRF لمزودي الذكاء الاصطناعي (S7)

**`lib/safe-outbound-url.ts` — كل نداء صادر يمر منها**: حفظ المزود، اختبار
الاتصال، المحادثة، سلسلة التراجع، custom-http، والمسار القديم في `lib/ai.ts`.

الطبقات:
1. **التحليل بـ`new URL()` فقط** — لا regex وحدها (شرط المواصفة).
2. **بروتوكولات**: http/https فقط — file/ftp/gopher/data/javascript/dict
   وكل ما عداهما مرفوض. **الإنتاج HTTPS فقط**؛ HTTP للتطوير/الاختبار
   (Ollama المحلي).
3. **userinfo مرفوض**، fragment مرفوض، query يرفض أنماط التحويل
   (`redirect=`)، المنافذ 1–65535 ومنافذ الخدمات الحساسة مرفوضة.
4. **أسماء محجوبة**: `localhost` و`.local` و`.internal` و`.localhost`
   وأسماء metadata السحابية، والأسماء الأحادية بلا نقطة (تُحل عبر نطاقات
   البحث الداخلية).
5. **المدى الخاص دائمًا محجوب** (تطويرًا وإنتاجًا): loopback، RFC1918
   (10/172.16-31/192.168)، CGNAT 100.64/10، link-local 169.254/16 (فيه
   169.254.169.254)، 0.0.0.0/8، multicast/reserved 224+، وIPv6: loopback
   وlink-local وULA fc00::/7 وmulticast و**IPv4-mapped IPv6 بنسختيه**
   (`::ffff:10.0.0.1` و`::ffff:a00:1` بعد تطبيع URL).
6. **قائمة مضيفي الإنتاج**: المضيف يجب أن يكون من القائمة المدمجة
   (api.openai.com، api.z.ai، api.deepseek.com، api.anthropic.com،
   generativelanguage.googleapis.com، api.groq.com) أو من
   `AI_PROVIDER_ALLOWED_HOSTS` الصريحة من المشغّل. لا مضيف اعتباطي يكتبه
   المدير يفتح الباب في الإنتاج.
7. **DNS (A + AAAA) قبل الاتصال**: أي عنوان محلول يقع في مدى خاص ⇒ رفض؛
   سجلات مختلطة عام+خاص ⇒ رفض.
8. **`redirect: "error"`** في كل fetch صادر: لا تتبع لتحويل يغيّر المضيف —
   الوجهة الثانية لم تُتحقق فنرفضها لا نتبعها.
9. **ترويسات المزود المخصصة**: المحجوبة (Host/Content-Length/Connection/
   Transfer-Encoding/Proxy-\*/X-Forwarded-\*/Cookie/Authorization/Forwarded)
   تُرفض عند الحفظ قبل أن تصل fetch يومًا.

**حد صادق — DNS rebinding**: التحقق ثم الاتصال ينفصلان بنافذة TOCTOU؛ تثبيت
DNS على الاتصال نفسه يتطلب وكيل اتصال مخصصًا لكل مضيف بنقطة فشل تشغيلية
أكبر من النافذة نفسها. مخاطرة rebinding **متبقية معلنة** ولا ندّعي حماية
كاملة منها. (في الاختبارات: حقن `fetchImpl` يعني بيئة متحكمًا بنقلها، فيتخطى
فحص DNS الحي ويبقى البنيوي كاملًا — وفحص DNS له اختباراته المخصصة بحاقن
`resolveDns`.)

## 9) حدود أجسام الطلبات (S8)

- **القارئ المركزي** `lib/http-body.ts`: `Content-Length` معلن يتجاوز الحد
  ⇒ 413 قبل أي قراءة؛ غائب (chunked) ⇒ القارئ نفسه يقطع عند الحد ويرمي
  413 — لا اعتماد على الترويسة وحدها. `413 لا 500` اختبار HTTP صريح.
- **الحدود** في `lib/security-limits.ts` (قابلة للتهيئة بالبيئة،
  افتراضات محافظة): JSON الداخلي 256KB، محادثة AI 1MB (تاريخ حوار غير
  محدود باب DoS وتكلفة)، الإعدادات 64KB، نماذج الدخول 128KB، رسائل
  الصوت/المرفقات 16MB (base64 لملف 10MB ≈ 14MB)، رفع المستندات 25MB
  (سقف 20MB القابل للتهيئة + هامش ترويسات multipart).
- **multipart**: يُقرأ bounded ثم يُفكك — فالحد قائم حتى مع غياب الطول
  المعلن. 20MB المسموح لا ينقطع، والضخم يُرفض 413 من طبقة الـproxy قبل
  الذاكرة.
- **طبقة proxy**: سقف Length المعلن لكل المسارات (JSON 2MB / رسائل 16MB /
  multipart 25MB) — شباك مبكر يغطي أي مسار لم يستخدم القارئ المركزي.
- **`proxyClientMaxBodySize`** (32MB): ضُبط تجريبيًّا فوق سقف الرفع،
  **موثَّق أنه experimental وليس الحارس الوحيد** — القارئ المحدود وسقف
  الـproxy هما الحكم.

## 10) بصمات الملفات (S9)

- **JPEG** (SOI+marker)، **PNG** (البصمة + chunk IHDR)، **WebP** (RIFF+WEBP
  + حجم الحاوية)، **PDF** (`%PDF-1.x` + `%%EOF` في الذيل) — فحص خفيف
  عمدًا بلا parser ثقيل؛ الهدف تمييز «هذا فعلًا من النوع المعلن».
- المُمَوّه يكتبه العميل؛ البايتات لا تكذب: ملف نصي/تنفيذي مدّعى PNG ⇒
  400 مع تسجيل تدقيق `document.upload.rejected_signature` — قبل أي كتابة
  على القرص.
- القائمة مغلقة كما كانت (JPEG/PNG/WebP/PDF) — لا DOCX/ZIP/SVG في P2.
- التخزين باقٍ **content-addressed** (مفتاح sha256 لا اسم المستخدم)، مع
  nosniff وCache-Control private/no-store والتفويض عند التنزيل وBOLA.
- مرفقات الرسائل لها فحص بصماتها الخاص منذ P0 (base64) — لم يُمسّ.
- المعاينة inline: نمط PDF يُعرض داخل iframe من نفس الأصل — القرار في §4.

## 11) حدود المعدل الموزعة (S10)

- **لا ذاكرة داخلية**: كل الحدود على PostgreSQL (نفس الجدول ونمط حدود
  الدخول الخضراء) — تعمل بين نسخ Railway ومع إعادة التشغيل.
- **حدود الدخول القائمة لم تُمسّ** — أُضيفت حدود جديدة للمناطق الناقصة:
  إعداد الحساب الأول (10/ساعة)، الحجز العام (30/15د نافذة قصيرة فوق
  الحدين اليوميّين القائمين)، تسجيل الوصول الذاتي (60/15د)، محادثة AI
  (30/5د لكل مستخدم)، اختبار اتصال مزود (10/5د لكل مدير).
- **المفاتيح بصمات HMAC** لا هوية خام: لا كلمات مرور ولا مفاتيح API ولا
  هواتف مرضى تُخزَّن في جدول الحدود.
- **429 + Retry-After** دائمًا، والاستجابة موحدة الشكل.
- **القيم في مكان واحد** (`lib/security-limits.ts`) قابلة للتهيئة
  بالبيئة — لا أرقام مبعثرة.
- **حد المصدر خلف وسيط موثّق فقط** (`TRUST_PROXY=true`) — كما في حدود
  الدخول.

## 12) الصحة والاستجابة والجاهزية (S11)

- **`/api/ping`**: نبض عام `{ok:true}` — لا قاعدة ولا تخزين ولا تفاصيل.
- **`/api/health`**: جاهزية minimal — 200 `{ready:true}` أو 503
  `{ready:false}` **فقط**. الحساب كامل خلف الرد (اتصال + سرّ + قاعدة
  تستجيب + تخزين دائم في الإنتاج) لكن المتصفح يرى الحكم النهائي — الجسم
  متطابق مهما اختلف سبب عدم الجاهزية. Railway healthcheck يبقى قادرًا على
  الاعتماد (200/503).
- **`/api/settings/readiness`** (مدير فقط): التفاصيل التشغيلية التي كانت
  تخرج للعابرين — نسخة الإصدار العاملة، كمون قاعدة البيانات، تشخيص
  التخزين الدائم التفصيلي، حالة SETUP_TOKEN (هل يجب حذفه) — وغير المدير
  401/403.

## 13) سياسة التخزين المؤقت (S12)

`/api/*` و`/portal/*` و`/print/*`: `Cache-Control: private, no-store` من
طبقة الـproxy — بيانات مرضى ومال ورسائل وطباعة لا تسكن أي cache مشترك.
الأصول الساكنة المتجزئة (`/_next/static`) خارج الحارس (تخزين حر)، ولا
معرفات مرضى في ETag. المسارات التي تضع سياقها (تنزيل المستندات) تبقى
سيادتها.

## 14) نظافة الأخطاء والسجلات (S13)

- `lib/redact.ts`: مفاتيح حساسة (password/secret/token/api-key/cookie/
  authorization) تُعقَّم `[معقّم]` قبل أي سجل تدقيق، وقيم سرّية معروفة
  الشكل (sk-/sk-ant-/AIza/gsk_) تُكتشف وتُعقَّم حتى تحت مفاتيح بريئة.
- `sanitizeErrorMessage`: أخطاء العميل لا تخرج بstack traces ولا مسارات
  ملفات ولا أسرار بيئة (SESSION_SECRET/DATABASE_URL/روابط postgres).
- أخطاء المزود تمر عبر `detail` الرسالة لا جسم upstream كاملًا.
- لا session token في عناوين أو سجلات التنزيل.
- أصلح في الطريق خطأً موجودًا مسبقًا: مسار الجاهزية كان يستعلم عمود
  `active` غير الموجود (الصحيح `is_active`) فكان يرد 500 للمدير.

## 15) مصفوفة RBAC/BOLA (S15)

على HTTP حقيقي ضد API مباشرة (لا أزرار واجهة) — الأدوار: مدير، طبيب أ،
طبيب ب، استقبال، محاسب، بوابة أ، بوابة ب، مجهول:

- طبيب أ ممنوع من قراءة/كتابة ملف مريض طبيب ب (patients/documents/PATCH)،
  وصفحات الطباعة تحترم نفس العزل (dossier).
- الاستقبال ممنوع من **كتابة** التوثيق السريري (CDS للطبيب والمدير)،
  والمحاسب كذلك؛ طبيب ب ممنوع من قراءة CDS زيارة مريض طبيب أ.
- الطبيب بلا canHandleMoney ممنوع من الدفعات؛ الاستقبال (صاحب المالية في
  نظام الأدوار الثلاثة) يصلها.
- بوابة أ ترى هويتها وبياناتها فقط — لا معرف مريض من العميل يبدل الهوية؛
  توكن البوابة لا يفتح مسارات الطاقم ولا العكس (فصل مجالات التوقيع).
- المجهول 401 على كل مسارات الطاقم؛ المحاسب بلا صلاحية AI ممنوع من
  المساعد؛ AI لا يتجاوز متصله (سياق مريض مسموم يُسقط ويُعلن).

ملاحظة نموذج الأدوار: النظام بني على ثلاثة أدوار (admin/doctor/reception)؛
حساب «محاسب» يرث افتراضيات الطبيب ما لم تُضبط صلاحياته صراحةً — لذلك تُعطى
بذور الاختبار صلاحيات صريحة (AI معطّل مثلًا) لتطابق دور محاسب مقيّد.

## 16) صحة الجلسات (S16)

- Credential Version قائم من P0: تغيير كلمة المرور/تعطيل الحساب يبطلان
  الجلسة القديمة (التحقق عند كل طلب من صف المستخدم الحالي).
- سمات خروج الطاقم/البوابة تطابق سمات دخولهما حرفيًّا (اختبار انحدار).
- توكن Bearer يُعاد في JSON لطلبات JSON غير-المتصفح فقط (تدفق API الموثق)؛
  متصفح الويب يأخذ كوكي HttpOnly — ولا تخزين localStorage للتوكنات.

## 17) السلسلة الغذائية وCI (S18)

CI يشغل بالترتيب الإلزامي: typecheck → unit (1359) → PostgreSQL (68) →
audit → build → **security-http (62)**. لا تخفيض لأي اختبار P0/P1:
سلامة الوصفات، تأكيدات AI، الردود/idempotency، append-only المالي،
baseline adoption، advisory lock، تدريب الاستعادة، تزامن WAC، دوام التخزين.

## 18) المخاطر المتبقية (صراحة كاملة)

1. **DNS rebinding** في بوابة SSRF (§8) — نافذة TOCTOU معلنة، تثبيتها
   يحتاج وكيل اتصال مخصصًا بقرار تشغيلي مستقل.
2. **CSP تغطي سكربتات Next المتولدة** — أي مكون مستقبلي يضيف سكربتًا
   خارجيًّا سينكسر بالتصميم (هذا هدف CSP لا نقصها)، ويجب أن يمر بمراجعة
   السياسة.
3. **حجم البصمة النصية للملف** في multipart: التحقق المركزي يقرأ bounded
   buffer (كما كان يفعل arrayBuffer) — الذاكرة مؤقتة ومرتدة، لكن طلبات
   رفع متزامنة كثيرة تستهلك ذاكرة تراكمية عابرة (سقف proxy يخففها).
4. **لا حد معدل على كل مسارات API الداخلية** — الحدود الجديدة للمناطق
   العامة والمكلفة؛ المسارات الداخلية خلف الجلسة وRBAC، وتوسيع الحدود
   إليها قرار تشغيلي عند الحاجة (البنية جاهزة: `consumeSecurityLimit`).
5. **`proxyClientMaxBodySize` تجريبي** (يمنحه Next) — موثَّق أنه ليس
   الحارس الوحيد، والحراس الفعلية القارئ المحدود وسقف الـproxy.
6. **توثيق Railway**: صيغة `RAILWAY_VOLUME_MOUNT_PATH` تُصادق أول تشغيل
   تشغيلي (من P1) — لم يتغير شيء هنا.
7. **لا Branch Protection منفذة** — توصية نهائية (§20) تُفعَّل بعد اعتماد
   P2 من مقر GitHub، لا من هذا الفرع.

## 19) الحدود ما قبل التفعيل النهائي

بوابات P0 + P1 + P2 كلها خضراء على بنية الاختبار المعزولة. لم يُنفَّذ:
migration على قاعدة الإنتاج، ولا Production Restore، ولا Deploy، ولا أي
تعديل على متغيرات Railway الإنتاجية — كلها **قرارات ما بعد اعتماد P2**
(بانتظار المراجعة المستقلة ثم التفعيل النهائي).

## 20) توصية حماية الفرع (بعد الاعتماد)

تُفعَّل من مقر GitHub بعد اعتماد P2 — لا من الكود:
- Require Pull Request قبل الدمج إلى main.
- Require CI (الخطوات الخمس + security-http) ناجحة.
- Disallow force push، وDisallow deletions على main.
- يُفضَّل Require branch up to date قبل الدمج.

```bash
npm run build
TEST_DATABASE_URL=postgresql://ci@127.0.0.1:55432/aqlan_p1_test?sslmode=disable \
  npm run test:security-http
```

المستعبِر ينشئ قاعدة معزولة (`aqlan_sec_http`) ويبذر أدوارًا ثمانية ومريضين،
ويشغّل الخادم المبني بproduction على منفذ معزول (3217 افتراضيًّا)، ثم يطفئه
ويسقط القاعدة في النهاية — لا لمس لأي بيئة إنتاج.
